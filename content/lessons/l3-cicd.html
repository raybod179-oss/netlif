۱

CI و CD یعنی چه؟

CI (یکپارچه‌سازی پیوسته): با هر push یا Pull Request، تست‌ها و بررسی‌های کیفیت خودکار اجرا می‌شود؛ اگر چیزی خراب بود، قبل از ورود به شاخه‌ی اصلی می‌فهمی. CD (تحویل/استقرار پیوسته): بعد از سبزشدن CI، نسخه خودکار روی سرور منتشر می‌شود. نتیجه: دیپلوی کم‌ترس و بدون «یادم رفت تست بزنم».

ابزار

در این درس از GitHub Actions استفاده می‌کنیم. اگر دسترسی به GitHub برایت محدود است، همین ایده با GitLab CI یا اجرای دستی اسکریپت دیپلوی ممکن است؛ سینتکس فرق می‌کند ولی مراحل یکی است.

۲

گردش‌کار CI: تست، سبک کد و امنیت

کدyaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  tests:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        php: ['8.3', '8.4']

    steps:
      - uses: actions/checkout@v4

      - name: Setup PHP
        uses: shivammathur/setup-php@v2
        with:
          php-version: ${{ matrix.php }}
          extensions: mbstring, intl, pdo_sqlite, bcmath, zip
          coverage: none

      - name: Cache Composer
        uses: actions/cache@v4
        with:
          path: ~/.composer/cache
          key: composer-${{ matrix.php }}-${{ hashFiles('composer.lock') }}

      - name: Install dependencies
        run: composer install --prefer-dist --no-interaction --no-progress

      - name: Prepare app
        run: |
          cp .env.example .env
          php artisan key:generate

      - name: Code style (Pint)
        run: ./vendor/bin/pint --test

      - name: Static analysis
        run: ./vendor/bin/phpstan analyse --memory-limit=1G

      - name: Tests
        run: php artisan test

      - name: Dependency audit
        run: composer audit
تست روی SQLite

تست‌ها معمولاً روی SQLite در حافظه اجرا می‌شوند (تنظیم در phpunit.xml) و نیازی به سرویس دیتابیس در CI نیست. اگر تست‌هایت MySQL واقعی می‌خواهند، در job یک services: mysql اضافه کن.

ابزارهای کیفیت: Pint و Larastan

کدbash
composer require laravel/pint --dev           # در پروژه‌های جدید معمولاً هست
composer require larastan/larastan --dev

./vendor/bin/pint                # اصلاح خودکار سبک کد
./vendor/bin/pint --test         # فقط بررسی (برای CI)
کدtext
# phpstan.neon
includes:
    - vendor/larastan/larastan/extension.neon

parameters:
    paths:
        - app/
    level: 5

با level: 5 شروع کن و کم‌کم بالا ببر. Larastan خطاهایی مثل فراخوانی متد ناموجود یا نوع اشتباه را قبل از اجرا می‌گیرد.

۴

استقرار خودکار با SSH

کدyaml
# .github/workflows/deploy.yml
name: Deploy

on:
  workflow_run:
    workflows: [CI]
    types: [completed]
    branches: [main]

jobs:
  deploy:
    if: ${{ github.event.workflow_run.conclusion == 'success' }}
    runs-on: ubuntu-latest
    environment: production        # می‌توانی در GitHub «تایید دستی» برای این محیط بگذاری

    steps:
      - name: Deploy over SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_KEY }}
          script: bash /var/www/myshop/deploy.sh
  • اسرار (SSH_HOST، SSH_USER، SSH_KEY) را در Settings ← Secrets and variables ← Actions بگذار؛ هرگز در فایل‌های ریپو.
  • برای دیپلوی یک کاربر و کلید SSH جدا با حداقل دسترسی بساز (فقط اجرای اسکریپت دیپلوی).
  • در Branch Protection شاخه‌ی main را قفل کن: بدون CI سبز و Pull Request امکان ادغام نباشد.
  • همان deploy.sh درس قبل را اینجا صدا می‌زنیم؛ یک منطق دیپلوی در یک جا.
Action از منابع ناشناس

هر Action شخص ثالث کد روی ماشین CI اجرا می‌کند. فقط از منابع معتبر و پرکاربرد استفاده کن و نسخه را ثابت نگه دار؛ در پروژه‌های حساس به‌جای Action، دستور ssh را مستقیم در مرحله‌ی run بنویس.

۶

جریان کار روزانه

  1. شاخه‌ی feature/... بساز و کد و تست بنویس.
  2. Push کن و Pull Request بزن؛ CI اجرا می‌شود.
  3. اگر قرمز بود، همان‌جا درست کن؛ سبز شد، ادغام کن.
  4. بعد از ادغام در main، CI و سپس Deploy خودکار اجرا می‌شود.
  5. اگر مشکلی پیش آمد، Revert کن (git revert) و دوباره Push کن.
۷

CI حرفه‌ای: دیتابیس واقعی، ماتریس نسخه و کش

تست روی SQLite حافظه‌ای سریع است، ولی خیلی از باگ‌ها فقط روی MySQL واقعی پیدا می‌شوند (collation، ایندکس یکتا، تراکنش). در GitHub Actions می‌توانی MySQL را به‌عنوان سرویس بالا بیاوری و هم‌زمان چند نسخه‌ی PHP را تست کنی.

کدyaml
# .github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  tests:
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        php: ["8.3", "8.4"]

    services:
      mysql:
        image: mysql:8.4
        env:
          MYSQL_DATABASE: testing
          MYSQL_ROOT_PASSWORD: secret
        ports: ["3306:3306"]
        options: >-
          --health-cmd="mysqladmin ping -h 127.0.0.1"
          --health-interval=10s --health-timeout=5s --health-retries=10

    steps:
      - uses: actions/checkout@v4

      - uses: shivammathur/setup-php@v2
        with:
          php-version: ${{ matrix.php }}
          extensions: mbstring, intl, pdo_mysql, bcmath
          coverage: none

      - name: Cache Composer
        uses: actions/cache@v4
        with:
          path: ~/.composer/cache
          key: composer-${{ matrix.php }}-${{ hashFiles('composer.lock') }}
          restore-keys: composer-${{ matrix.php }}-

      - run: composer install --no-interaction --prefer-dist --no-progress
      - run: cp .env.example .env && php artisan key:generate

      - name: Style (Pint)
        run: ./vendor/bin/pint --test

      - name: Tests
        env:
          DB_CONNECTION: mysql
          DB_HOST: 127.0.0.1
          DB_PORT: 3306
          DB_DATABASE: testing
          DB_USERNAME: root
          DB_PASSWORD: secret
        run: php artisan test --parallel
  • concurrency: اگر پشت‌سرهم Push کردی، اجرای قدیمی لغو می‌شود و وقت هدر نمی‌رود.
  • matrix: همان تست‌ها روی هر دو نسخه‌ی PHP اجرا می‌شود؛ اگر یکی شکست خورد، خطای سازگاری را زود می‌فهمی.
  • --parallel نیاز به پکیج brianium/paratest دارد؛ اگر ندارید حذفش کن یا آن را به‌صورت dev نصب کن.
  • pint --test فقط بررسی می‌کند و فایل را عوض نمی‌کند؛ اگر استایل خراب باشد Job قرمز می‌شود.
اگر GitHub برایت در دسترس نیست

دسترسی به GitHub و Actions برای بعضی کاربران ایران محدود یا ناپایدار است. همان منطق (نصب → تست → ساخت → استقرار) را می‌شود با GitLab CI، Gitea/Forgejo با Runner خودت، یا حتی یک اسکریپت deploy.sh روی سرور اجرا کرد. مفهوم مهم‌تر از ابزار است.

۸

Secret، محیط‌ها و محافظت از شاخه‌ی اصلی

هیچ‌وقت رمز یا کلید SSH را داخل مخزن نگذار. GitHub سه جا برای نگه‌داری آن‌ها دارد:

محلکاربرد
Repository secretsمقدارهای مشترک همه‌ی Jobها (مثلاً توکن اعلان تلگرام)
Environment secretsمقدارهای مخصوص staging یا production؛ می‌شود برای Production «تأیید دستی» خواست
Variablesمقدارهای غیرمحرمانه مثل آدرس سایت
  1. در Settings ← Environments دو محیط staging و production بساز؛ برای production گزینه‌ی Required reviewers را روشن کن تا هر استقرار به تأیید تو نیاز داشته باشد.
  2. در Settings ← Branches برای main یک Branch protection بگذار: «Require a pull request» و «Require status checks to pass» (Job تست را انتخاب کن). حالا کد خراب مستقیم وارد main نمی‌شود.
  3. برای SSH یک کلید جدا و فقط برای استقرار بساز: ssh-keygen -t ed25519 -f deploy_key -C "github-deploy". کلید عمومی را در ~/.ssh/authorized_keys سرور بگذار و کلید خصوصی را در Secret به نام SSH_KEY ذخیره کن.
اگر Secret لو رفت

فوراً آن را در GitHub حذف و کلید/رمز را در سرور باطل کن و نسخه‌ی تازه بساز. Secretها در لاگ‌ها ماسک می‌شوند، ولی هرگز آن‌ها را echo نکن.

۹

استقرار خودکار با SSH و اسکریپت امن

بعد از موفق بودن تست‌ها روی main، یک Job دوم سرور را به‌روز می‌کند. منطق اصلی در یک اسکریپت روی سرور است تا هم دستی و هم از CI قابل اجرا باشد.

کدyaml
  deploy:
    needs: tests
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Prepare SSH
        run: |
          mkdir -p ~/.ssh
          echo "${{ secrets.SSH_KEY }}" > ~/.ssh/id_ed25519
          chmod 600 ~/.ssh/id_ed25519
          ssh-keyscan -H "${{ secrets.SSH_HOST }}" >> ~/.ssh/known_hosts

      - name: Deploy
        run: ssh ${{ secrets.SSH_USER }}@${{ secrets.SSH_HOST }} 'bash /var/www/shop/deploy.sh'
کدbash
#!/usr/bin/env bash
# /var/www/shop/deploy.sh
set -euo pipefail
cd /var/www/shop

php artisan down --retry=60 --refresh=15
trap 'php artisan up' EXIT        # حتی اگر خطا شد، سایت از حالت تعمیر بیرون بیاید

git fetch --all --prune
git reset --hard origin/main

composer install --no-dev --no-interaction --prefer-dist --optimize-autoloader
npm ci && npm run build

php artisan migrate --force
php artisan optimize
php artisan queue:restart
echo "Deployed: $(git rev-parse --short HEAD)"
خطاگیری

set -euo pipefail یعنی با اولین خطا اسکریپت متوقف شود (نه اینکه ادامه بدهد و سایت نیمه‌کاره بماند). trap هم تضمین می‌کند سایت در حالت تعمیر باقی نماند.

ایراد این روش: بین down و up چند ثانیه سایت در دسترس نیست. برای پروژه‌های بزرگ‌تر از ساختار «release» استفاده می‌کنند.

کدbash
# ساختار بدون وقفه (Zero-downtime)
/var/www/shop/
  releases/20261019-1030/    ← هر استقرار یک پوشه‌ی جدید
  releases/20261019-1500/
  shared/.env  shared/storage/   ← چیزهایی که بین releaseها مشترک است
  current -> releases/20261019-1500   ← لینک نمادین؛ Nginx به current/public اشاره می‌کند

# جابه‌جایی نسخه فقط عوض‌کردن یک لینک است (تقریباً لحظه‌ای)
ln -sfn /var/www/shop/releases/20261019-1500 /var/www/shop/current
# برگشت به نسخه‌ی قبل (Rollback)
ln -sfn /var/www/shop/releases/20261019-1030 /var/www/shop/current
php artisan queue:restart
۱۰

بازگشت (Rollback)، هشدار و کنترل کیفیت

  • Migration را رو به عقب‌سازگار بنویس: ستونِ جدید را اول nullable اضافه کن و کد جدید را بیاور؛ حذف ستون قدیمی را در استقرار بعدی انجام بده. این‌طور بازگشت به کد قدیمی امن می‌ماند.
  • قبل از migrate بکاپ بگیر (دستور mysqldump را در همان اسکریپت استقرار بگذار).
  • هشدار: یک مرحله‌ی آخر که در صورت شکست استقرار، پیام تلگرام یا ایمیل بفرستد (if: failure()).
  • بررسی بعد از استقرار (Smoke test): مثلاً curl -fsS https://example.com/up؛ لاراول مسیر سلامت /up را به‌صورت پیش‌فرض دارد.
  • برچسب نسخه: بعد از استقرار موفق، یک Tag مثل v1.4.0 بزن تا همیشه بدانی چه چیزی روی سرور است.
کدyaml
      - name: Smoke test
        run: curl -fsS --retry 5 --retry-delay 5 https://example.com/up

      - name: Notify on failure
        if: failure()
        run: >
          curl -s -X POST "https://api.telegram.org/bot${{ secrets.TG_TOKEN }}/sendMessage"
          -d chat_id="${{ secrets.TG_CHAT }}"
          -d text="❌ Deploy failed: ${{ github.repository }} @ ${{ github.sha }}"
۱۱

اشتباه‌های رایج

  1. قرار دادن اسرار در فایل workflow یا لاگ‌ها.
  2. تست‌هایی که فقط روی سیستم خودت پاس می‌شوند (به ترتیب یا داده‌ی محلی وابسته‌اند).
  3. نداشتن Branch Protection و ادغام مستقیم کد قرمز.
  4. دیپلوی خودکار بدون راه بازگشت و بدون بکاپ قبل از migrate.
  5. نادیده‌گرفتن هشدار composer audit.
  6. CI خیلی کند؛ کش و موازی‌سازی را رعایت کن.
  7. گذاشتن کلید SSH یا رمز در مخزن به‌جای Secret.
  8. استقرار از شاخه‌ی اشتباه یا بدون اجرای تست (نبودن needs: tests).
  9. اجرای migrate مخرب (حذف ستون) هم‌زمان با کد جدید و غیرممکن‌شدن بازگشت.
★

تمرین‌ها

تمرین ۱
  1. Pint و Larastan را به پروژه اضافه کن و فایل CI را بنویس؛ یک تست را عمداً خراب کن و ببین Action قرمز می‌شود.
تمرین ۲
  1. Branch Protection را روی main فعال کن و یک Pull Request واقعی بزن.
  2. نشان CI را به README پروژه‌ات اضافه کن.
تمرین ۳
  1. اگر سرور داری، Deploy خودکار را با Secretها راه بینداز؛ سپس یک تغییر کوچک را فقط با Merge منتشر کن.
تمرین ۴
  1. یک Workflow برای مخزنت بنویس که با هر Pull Request تست و Pint را اجرا کند و برای main قانون «بدون تست سبز merge نشود» بگذار.
  2. عمداً یک تست را خراب کن و ببین Job قرمز می‌شود و merge بسته می‌شود.
تمرین ۵
  1. اسکریپت deploy.sh را روی یک VPS یا سرور آزمایشی بگذار و یک بار دستی اجرا کن؛ سپس ساختار releases/current را پیاده کن و یک Rollback امتحان کن.
