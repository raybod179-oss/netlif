۱

سفرِ یک درخواست تا پاسخ

هر چیزی که در روت یا کنترلر return شود، لاروال آن را به یک پاسخ HTTP تبدیل می‌کند و با یک «کد وضعیت» به مرورگر می‌فرستد. پس همان‌جایی که تا الان return 'متن' می‌نوشتی، در واقع داری پاسخِ صفحه را می‌سازی. مسیرِ کامل را این‌طور ببین:

مرورگر → روت → کنترلر → پاسخ (return) ← مرورگر

کدِ وضعیت، نتیجه‌ی درخواست را به مرورگر می‌گوید. مهم‌ترین‌ها:

  • 200 = موفق.
  • 302 = ریدایرکت (بعداً در همین بخش).
  • 404 = پیدا نشد (بخش ۰۳ با abort ساختیمش).
  • 403 = مجاز نیستی · 500 = خطای سرور.

حالا ببین لاروال هر نوعِ return را چطور تبدیل می‌کند — تا الان فقط ردیفِ اول را دیده‌ای:

کدچه برمی‌گردانی؟
شما برمی‌گردانید پاسخی که مرورگر می‌گیرد کی به‌کار می‌آید
return 'متن ساده'; HTML ساده که تا الان کرده‌ایم
return ['key' => 'value']; JSON (خودکار) API و درخواست‌های جاوااسکریپت
return view('...'); HTML بخش ۰۵ (Blade)
return response()->json([...]); JSON با کنترل کامل همین بخش بعدی
return redirect('/x'); 302 + هدر Location بعد از عملیات (همین بخش)
خلاصه

«درخواست» چیزی است که می‌آید، «پاسخ» چیزی است که برمی‌گردد؛ و کد وضعیت روایت می‌کند که چه شد. این دو + سشن، تمام مباحثِ بقیه‌ی بخش است.

۲

خواندن ورودی‌ها

کاربر داده را با query string (?q=کفش) یا بعداً با فرم (POST) می‌فرستد. هر دو را از روی همان شیء Request (که در بخش ۰۳ تزریق کردیم) می‌خوانیم:

کدPHP — در کنترلر
public function search(Request $request)
{
    $q      = $request->query('q');                          // فقط از query string
    $sort   = $request->input('sort', 'newest');            // از هرجا؛ با مقدار پیش‌فرض
    $all    = $request->all();                              // همه‌ی ورودی‌ها (آرایه)
    $proxy  = $request->only(['q', 'sort']);                // فقط همین چند کلید

    return "جست‌وجو: $q | مرتب‌سازی: $sort";
}
  • $request->query('q') فقط از query string می‌خواند؛ $request->input('sort') از کل بدنه (query + فرمِ POST).
  • به هر دو می‌توانی مقدارِ پیش‌فرض بدهی: input('sort', 'newest') — اگر نبود، پیش‌فرض برمی‌گردد، نه null.
  • only(...) فقط کلیدهای مشخص را برمی‌گرداند؛ except(...) همه‌ی کلیدها «جز» آن‌ها را (برای نرسیدنِ رمزعبور به جای دیگر به‌درد می‌خورد).

و «آیا فلان ورودی هست؟» — با این دستورها (حضور در مقابل پُربودن):

کدPHP
if ($request->has('q')) { }        // هست؟ حتی اگر خالی باشد: true
if ($request->filled('q')) { }     // هست و پُر است؟ (خالی = false)
if ($request->missing('q')) { }    // نیست؟
if ($request->hasAny(['q', 'tag'])) { } // دستِ کم یکی هست؟
چند ضروریِ کاربردی
  • تبدیل خودکار تایپ: $request->boolean('active') مقدارهای چک‌باکس مثل "on"/"1" را true می‌کند؛ و $request->integer('page') عدد تحویل می‌دهد.
  • دسترسیِ کوتاه: $request->name همان فیلدِ name است (مثل خواصِ آبجکت).
  • پاک‌سازی خودکار: لاروال به‌صورت پیش‌فرض فاصله‌های ابتدا/انتهای متن‌ها را می‌تراشد (TrimStrings) و رشته‌ی خالی را null می‌کند. پس لازم نیست خودت trim() بزنی.
۳

خودِ درخواست؛ روش‌ها و هدرها

گاهی به «محتوا»ی درخواست کار ندارد؛ به «خودِ درخواست» کار دارد: چه روشی (GET/POST)، کدام مسیر، آدرس کامل، یک هدر یا IP بازدیدکننده. همه روی همان $request است:

کدPHP
public function meta(Request $request)
{
    $method = $request->method();       // "GET"
    $isPost = $request->isMethod('post');

    $path   = $request->path();         // "products/2"
    $admin  = $request->is('admin/*');  // آیا مسیر admin/... است؟

    $short  = $request->url();          // بدون query string
    $full   = $request->fullUrl();      // با query string

    $agent  = $request->header('User-Agent');
    $ip     = $request->ip();

    $method  = $admin ? 'part of admin' : $path;
    return "$method | $agent";
}
خروجی نمونهچه می‌بینی؟
بازدید از /products/2?q=کفش:
  • method() → GET
  • path() → products/2
  • is('admin/*') → false
  • url() → …/products/2
  • fullUrl() → …/products/2?q=کفش
  • ip() → 127.0.0.1
به چه درد می‌خورند؟
  • path() و is(): کل صفحه‌های «پنل مدیریت» با is('admin/*') — بعداً برای سطح دسترسی.
  • header(): زبان مرورگر، توکن احراز هویت و... — در بخش‌های Middleware و API.
  • ip(): نمایش IP مشتری در سفارش، و Rate Limit ضدِ هرزنامه (بخش ۱۵).
۴

ساختنِ پاسخِ دلخواه

وقتی فقط return 'متن' می‌کنی، لاروال خودش کدِ وضعیت 200 و هدرها را می‌سازد. برای کنترلِ کامل، از تابعِ راحتیِ response() استفاده کن — زنجیره‌ای:

کدPHP
// متن با کد وضعیت و هدر دلخواه
return response('ساخته شد', 201)
        ->header('Content-Type', 'text/plain');

// پاسخ JSON برای API / جاوااسکریپت
return response()->json([
    'ok'   => true,
    'data' => ['products' => []],
]);

// چند هدر یکجا
return response('...')
        ->withHeaders(['X-Debug' => 'on',
                       'Cache-Control' => 'no-store']);
خروجی نمونهچه می‌بینی؟
برگرداندنِ آرایه:
HTTP/1.1 200 OK content-type: application/json { "name": "علی", "age": 30 }
آرایه‌ی ساده هم خودکار JSON می‌شود؛ بدون اینکه response()->json() بنویسی.
بقیه‌ی پاسخ‌های آماده

این‌ها را الان فقط بشناس تا وقتی بدانیم سراغشان می‌رویم:

  • response()->view('name', $data, 200) → ویو با کد وضعیت (کاربردی وقتی می‌خواهی 404 دلخواه بسازی).
  • response()->download($path, $filename) → دانلود فایل (مثلاً فاکتور) — در بخش Storage کاملش می‌سازیم.
  • response()->file($path) → نمایش فایلِ تصویر/PDF در مرورگر.
۵

ریدایرکت‌کردن

ریدایرکت، یک پاسخ 302 است که به مرورگر می‌گوید «برو به یک آدرس دیگر». پرکاربردترین روش‌هایش:

کدPHP
// ۱) به یک آدرس ساده
return redirect('/products');

// ۲) به یک مسیرِ نامدار — با پارامتر
return redirect()->route('products.show', ['id' => 3]);

// ۳) ببر عقب به همان صفحه‌ای که فرم از آن آمده بود
return back();

// ۴) به یک دامنه‌ی بیرونی (مثلاً درگاه پرداخت)
return redirect()->away('https://example.com');
قانونِ طلایی: بعد از عملیاتِ تغییردهنده، ریدایرکت کن

هر وقت کاربر چیزی «می‌سازد/می‌فرستد» (POST — بخش ۱۰ با فرم‌ها)، هیچ وقت return 'متن' نده؛ با ریدایرکت‌کردن، اگر کاربر F5 بزند، عملیات دوباره اجرا نمی‌شود (مثلاً سبدِ تکراری).

Tوی شبکه، ریدایرکت این‌طور دیده می‌شود (تب Network ابزارِ توسعه‌دهنده را باز کن):

کدخروجی نمونه — هدر پاسخ
HTTP/1.1 302 Found location: /products/3 set-cookie: XSRF-TOKEN=…; laravel_session=…
چرا برگشتنِ به «قبلی» مهم است؟

back() یعنی «همان صفحه‌ی قبلی»؛ فرمی که پر کردی و خطا داد، با back()->withInput() دوباره پر می‌شود. این کار با سشن اجرا می‌شود — برویم سراغش.

۶

سشن و پیامِ فلش

HTTP «بی‌حافظه» است: هر درخواست، یک دنیای تازه است. سشن این را حل می‌کند — داده‌ی کاربر را بین درخواست‌ها نگه می‌دارد. ساده‌ترین کاربردش پیامِ فلش است: «این پیام فقط برای درخواستِ بعدی زنده باشد» (مثلاً پیامِ موفقیت بعد از عملیات):

کدPHP — بعد از یک عملیات موفق
public function addToCart()
{
    // ... محصول توی سبد گذاشته شد

    return redirect()->route('cart.index')
        ->with('status', 'به سبد خرید اضافه شد');
}

در درخواستِ بعدی، پیام را با تابعِ session('status') می‌خوانیم. (نمایشِ آن در Blade است — در بخش ۰۵ کامل یاد می‌گیری؛ این را همین‌جا فقط ببین):

کدBlade — پیش‌نمایش (بخش ۰۵)
@if (session('status'))
    <div class="alert">{{ session('status') }}</div>
@endif

پایه‌ی همین مفهوم — ذخیره‌ی ماندگارتر در سشن:

کدPHP
// ذخیره برای چند درخواست (ماندگارتر از فلش)
session(['cart_count' => 3]);          // یا:
$request->session()->put('cart_count', 3);

// خواندن با پیش‌فرض
$count = session('cart_count', 0);

// آیا کلیدی هست؟ — پایه‌ی «اگر چیزی در سبد هست، نشان بده»
$has = $request->session()->has('cart_count');

// خواندن و حذفِ یکجا
$val = $request->session()->pull('cart_count');

// حذف
session()->forget('cart_count');
فلش در مقابل ورودیِ قدیمی (old)
  • ->with('status', ...) برای «پیام» است و با session('status') خوانده می‌شود.
  • ->withInput() ورودی‌های فرم را برای درخواستِ بعدی نگه می‌دارد تا old('name') بتواند فرم را دوباره پر کند — وقتی اعتبارسنجی خطا داد (در بخش ۱۰ با فرم‌ها).
  • فلش یک عمرِ کوتاه دارد: دقیقاً «همان درخواستِ بعدی». اگر بیشتر لازم بود: reflash() یا keep().
۷

دیباگ با dd و dump

وقتی می‌خواهی ببینی چیزی «الان‌ها واقعاً چیست»، دو تابعِ راحت داری. البته فقط برای زمانِ توسعه:

کدPHP — فقط دیباگ
// چاپ کن و بایست
dd($request->all(), $request->method());

// چاپ کن اما ادامه بده
dump($request->query());
خروجی نمونهdd(...)
dd($request->all(), $request->method()); // app\Http\Controllers\X array:1 [ "q" => "کفش" ] "GET" Last 10 lines executed…
  • dd(...) = dump and die: مقدار را مرتب چاپ می‌کند و اجرا را همان‌جا قطع می‌کند — سریع‌ترین راهِ فهمیدنِ «چه‌چیزی می‌رسد».
  • dump(...) مثل dd است ولی اجرا ادامه پیدا می‌کند.
  • هر جایِ کد — روت، کنترلر، حتی داخل حلقه — می‌توانی dd بگذاری و بروی جلو.
هیچ وقت در عملیاتِ واقعی

dd و dump فقط روی سیستمِ توسعه. قبل از عملیات، همه را پاک کن. اگر چیزی خواستی «ثبت» شود ولی سایت برگردد، از logger()->info('پیام', $data) استفاده کن که در storage/logs/laravel.log نوشته می‌شود.

۸

گام پروژه: این‌ها کجای فروشگاه می‌نشینند؟

همین‌جا کاملش نمی‌کنیم؛ فقط نقشه‌اش را ببین

این‌جا قصد نداریم کدی بنویسیم — فقط بفهم «هر وسیله‌ای که امروز یاد گرفتی، فردا در کدام صفحه‌ی فروشگاه استفاده می‌شود»:

  • ورودی‌ها (query/input): فهرستِ محصولات با ?search=... و مرتب‌سازی ?sort=price؛ و صفحه‌بندی با integer('page').
  • اطلاعات درخواست: is('admin/*') برای جداسازی صفحه‌های مدیریت؛ ip() برای ثبت در سفارش.
  • ریدایرکت + فلش: بعد از «افزودن به سبد» → ریدایرکت به سبد با پیامِ «`با موفقیت اضافه شد`»؛ بعد از ثبت سفارش → صفحه‌ی سفارش با پیامِ موفقیت.
  • withInput: فرمِ «افزودن محصول» در پنلِ مدیریت (وقتی خطای اعتبارسنجی دارد، فرم خالی نشود) — در بخش ۱۰.
  • dd: ابزارِ تو برای فهمیدنِ این‌که واقعاً چه اطلاعاتی از یک صفحه به کنترلر می‌رسد.
پیاده‌سازیِ واقعی این‌ها کجاست؟

همه‌ی این‌ها وقتی معنا می‌شوند که مدل و Blade داشته باشیم؛ پس پیاده‌سازیِ کاملشان – کنترلرِ سبد، فرم‌ها، صفحه‌بندی – در بخش‌های بعد و در «بخش ۹۹: پروژه‌ی پایانی» جمع می‌شود. فعلاً فقط ابزارها را بلدید.

۹

تمرین‌ها؛ حالا نوبت توست!

تمرین ۱: ورودی‌شناسی
  1. یک کنترلر EchoController بساز با متدِ peek(Request $request).
  2. همه‌ی ورودی‌ها را با dd($request->all()) نشان بده.
  3. روتش را بگذار: /echo و این آدرس‌ها را تست کن: /echo?name=ali&age=30 و /echo?name=ali. تفاوتِ filled را با has روی age چه‌طور می‌بینی؟
تمرین ۲: ریدایرکت و فلش
  1. یک روت /go بساز که redirect()->route('products.show', ['id' => 2])->with('status', 'به سبد اضافه شد') برگرداند.
  2. یک روت دیگر /flash-check بِردار که session('status', 'پیامی نیست') را برگرداند.
  3. اول /go را باز کن، بعد /flash-check؛ حالا یک‌بار دیگر /flash-check را رفرش کن — ببین فلش چرا ناپدید شد!
چالش

یک روت /info بساز که متد، مسیر، آدرسِ کامل، هدر User-Agent و IP را در یک آرایه برگرداند. ببین مرورگر چطور JSON را نشان می‌دهد — بی‌اینکه response()->json() بنویسی. (اگر لوکال تست می‌کنی، IP یعنی 127.0.0.1.)

چیزی که از این بخش توی ذهنت بماند

  1. هر returnی به پاسخ HTTP تبدیل می‌شود؛ متن → HTML، آرایه → JSON، و redirect() → 302.
  2. ورودی‌ها: query() فقط query string، input() همه‌جا؛ همیشه پیش‌فرض بده.
  3. حضور با has، پُربودن با filled؛ گزینش با only/except.
  4. method/path/is/url/header/ip اطلاعاتِ خودِ درخواست‌اند.
  5. پاسخِ دلخواه: response($content, $status)->header(...) و response()->json([...]).
  6. بعد از هر عملیاتِ تغییردهنده ریدایرکت کن؛ redirect()->route(...) و back().
  7. فلش فقط برای «درخواستِ بعدی» زنده است: ->with('status', ...) و خواندن با session('status').
  8. withInput() ورودی‌های فرم را برای old() نگه می‌دارد (بخش ۱۰).
  9. dd()/dump() فقط در توسعه؛ در عملیات از logger() استفاده کن.
مطالعه‌ی بیشتر (انگلیسی): خواندن ورودی‌ها و حضور/پر بودن (has/filled)، ریدایرکت‌ها و ریدایرکتِ همراه با فلش، ذخیره و خواندن در سشن و Flash Data.
