چرا تست بنویسیم؟

تست یعنی کدی که کد دیگر را خودکار چک می‌کند. وقتی پروژه بزرگ شود، هر تغییر ممکن است چیزی را خراب کند؛ تست‌ها در چند ثانیه می‌گویند «همه‌چیز هنوز کار می‌کند؟». پروژه‌های جدی (و مصاحبه‌های کاری) تست را می‌خواهند.

نوعچه چیزی را می‌سنجد؟سرعت
Unitیک کلاس یا تابع تنها (مثل محاسبه‌ی جمع سبد)خیلی سریع
Featureیک درخواست کامل: روت ← کنترلر ← دیتابیس ← پاسخسریع
Browser (Dusk)مرورگر واقعیکند؛ در این دوره نیست

اجرای اولین تست

کدbash
php artisan test                       # اجرای همه‌ی تست‌ها
php artisan test --filter=ProductTest  # فقط یک کلاس/متد
php artisan test --parallel            # موازی (سریع‌تر)

php artisan make:test ProductTest          # Feature test
php artisan make:test CartTest --unit      # Unit test
دیتابیس تست

فایل phpunit.xml را باز کن؛ معمولاً تست‌ها روی SQLite در حافظه (:memory:) اجرا می‌شوند تا دیتابیس اصلی‌ات دست‌نخورده بماند و تست‌ها سریع باشند. هرگز تست را روی دیتابیس واقعی اجرا نکن.

۳

Feature Test: درخواست واقعی

کدphp
<?php

namespace Tests\Feature;

use App\Models\Product;
use App\Models\User;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

class ProductTest extends TestCase
{
    use RefreshDatabase;   // قبل از هر تست دیتابیس تمیز می‌شود

    public function test_products_page_lists_products(): void
    {
        Product::factory()->count(3)->create();

        $response = $this->get('/products');

        $response->assertStatus(200);
        $response->assertViewHas('products');
    }

    public function test_guest_cannot_create_product(): void
    {
        $this->post('/admin/products', ['title' => 'x'])
             ->assertRedirect('/login');
    }

    public function test_admin_can_create_product(): void
    {
        $admin = User::factory()->create(['role' => 'admin']);

        $this->actingAs($admin)
             ->post('/admin/products', [
                 'title' => 'کیبورد',
                 'price' => 850000,
                 'stock' => 5,
             ])
             ->assertRedirect();

        $this->assertDatabaseHas('products', ['title' => 'کیبورد', 'price' => 850000]);
    }

    public function test_validation_fails_without_title(): void
    {
        $admin = User::factory()->create(['role' => 'admin']);

        $this->actingAs($admin)
             ->post('/admin/products', ['price' => 100])
             ->assertSessionHasErrors('title');
    }
}
نام تست

نام متد را مثل یک جمله‌ی کوتاه بنویس: test_guest_cannot_create_product. وقتی تستی fail شد، همین نام می‌گوید چه چیزی خراب شده.

Unit Test و Factory

کدphp
<?php

namespace Tests\Unit;

use App\Services\CartCalculator;
use PHPUnit\Framework\TestCase;

class CartCalculatorTest extends TestCase
{
    public function test_discount_applies_over_one_million(): void
    {
        $calc = new CartCalculator();

        $this->assertSame(900000, $calc->payable(1000000)); // ۱۰٪ تخفیف
        $this->assertSame(500000, $calc->payable(500000));  // بدون تخفیف
    }
}
کدphp
<?php

namespace Database\Factories;

use Illuminate\Database\Eloquent\Factories\Factory;

class ProductFactory extends Factory
{
    public function definition(): array
    {
        return [
            'title' => fake()->words(2, true),
            'price' => fake()->numberBetween(50000, 2000000),
            'stock' => fake()->numberBetween(0, 50),
        ];
    }

    public function outOfStock(): static
    {
        return $this->state(fn () => ['stock' => 0]);
    }
}

// استفاده: Product::factory()->outOfStock()->create();

Fake: ایمیل، صف و رویداد را بدون اجرای واقعی تست کن

کدphp
<?php

namespace Tests\Feature;

use App\Jobs\SendOrderReport;
use App\Mail\OrderPaid;
use App\Models\Order;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Illuminate\Support\Facades\Mail;
use Illuminate\Support\Facades\Queue;
use Tests\TestCase;

class OrderFlowTest extends TestCase
{
    use RefreshDatabase;

    public function test_paid_order_sends_mail_and_dispatches_job(): void
    {
        Mail::fake();
        Queue::fake();

        $order = Order::factory()->create();
        // ... ثبت پرداخت (کد برنامه‌ی تو) ...

        Mail::assertSent(OrderPaid::class);
        Queue::assertPushed(SendOrderReport::class);
    }
}

برای درخواست‌های بیرونی (مثل درگاه پرداخت) هم از Http::fake() استفاده می‌کنیم تا تست‌ها هیچ‌وقت به اینترنت وصل نشوند (در درس درگاه می‌بینی).

۷

ریتم کار: قرمز، سبز، بازنویسی

  1. قرمز: اول تستی بنویس که fail می‌شود (چون قابلیت هنوز نیست).
  2. سبز: کمترین کدی را بنویس که تست pass شود.
  3. بازنویسی: کد را تمیز کن؛ تست نگهبان توست که چیزی خراب نشود.
از کجا شروع کنیم؟

نیازی نیست همه‌چیز را تست کنی. اول بخش‌های حساس: ورود، سفارش و پرداخت، دسترسی‌ها (ادمین/کاربر) و محاسبات پول.

۸

تست‌های واقعی‌تر: API بیرونی، زمان و Mock

تست خوب نباید به اینترنت، ساعت واقعی یا سرویس پیامک وابسته باشد. لاراول برای همه‌ی این‌ها ابزار آماده دارد.

کدphp
use Illuminate\Support\Facades\Http;

public function test_payment_verify_marks_order_paid(): void
{
    Http::fake([
        'gateway.test/verify*' => Http::response(['status' => 'success', 'ref' => 'ABC123'], 200),
    ]);

    $order = Order::factory()->create(['status' => 'pending']);

    $this->actingAs($order->user)
         ->get(route('payment.callback', ['order' => $order, 'token' => 'x']))
         ->assertRedirect(route('orders.show', $order));

    $this->assertSame('paid', $order->fresh()->status);
    Http::assertSent(fn ($request) => str_contains($request->url(), 'gateway.test/verify'));
}

// ساعت را کنترل کن
public function test_unpaid_orders_expire_after_30_minutes(): void
{
    $order = Order::factory()->create(['status' => 'pending']);

    $this->travel(31)->minutes();
    $this->artisan('orders:release-unpaid')->assertSuccessful();

    $this->assertSame('cancelled', $order->fresh()->status);
}

// سرویس را Mock کن
public function test_sms_is_sent_on_registration(): void
{
    $this->mock(SmsSender::class, function ($mock) {
        $mock->shouldReceive('send')->once()->with('09120000000', \Mockery::type('string'));
    });

    $this->post('/register', [/* ... */])->assertRedirect();
}
قانون ساده

همه‌چیز بیرون از برنامه (HTTP، ایمیل، پیامک، صف، زمان) را در تست Fake یا Mock کن؛ هر چه داخل برنامه است (دیتابیس، Eloquent، Routeها) را واقعی بگذار. تست‌ها هم سریع می‌شوند و هم قابل‌اعتماد.

داده‌محور، Factory State و سرعت

به‌جای نوشتن ده تست شبیه هم برای ورودی‌های مختلف، یک تست با چند داده بنویس:

کدphp
use PHPUnit\Framework\Attributes\DataProvider;

#[DataProvider('invalidPhones')]
public function test_phone_validation_fails(string $phone): void
{
    $this->post('/register', ['phone' => $phone] + $this->validData())
         ->assertSessionHasErrors('phone');
}

public static function invalidPhones(): array
{
    return [
        'کوتاه'      => ['0912'],
        'حروف'       => ['0912abcdefg'],
        'پیش‌شماره'  => ['02112345678'],
        'خالی'       => [''],
    ];
}
کدphp
// database/factories/OrderFactory.php: حالت‌های آماده (State)
public function paid(): static
{
    return $this->state(fn () => ['status' => 'paid', 'paid_at' => now()]);
}
public function withItems(int $n = 3): static
{
    return $this->has(OrderItem::factory()->count($n), 'items');
}

// در تست
$order = Order::factory()->paid()->withItems(2)->create();
کدbash
php artisan test --parallel            # اجرای موازی (نیاز به paratest)
php artisan test --filter=payment      # فقط تست‌هایی که اسمشان شامل payment است
php artisan test --stop-on-failure     # با اولین خطا متوقف شو
php artisan test --coverage --min=70   # پوشش تست؛ نیاز به PCOV یا Xdebug
  • RefreshDatabase برای هر تست دیتابیس را تمیز می‌کند. با SQLite حافظه‌ای سریع است، ولی قبل از انتشار یک بار روی MySQL واقعی هم اجرا کن.
  • تست «مسیر شاد» (Happy path) کافی نیست: ورودی نامعتبر، کاربر بدون دسترسی و حالت خالی را هم تست کن.
  • هر باگی که در پروداکشن پیدا کردی، اول یک تست بنویس که آن را نشان دهد، بعد درستش کن. این‌طور دوباره برنمی‌گردد.
۱۰

اشتباه‌های رایج

  1. فراموش‌کردن RefreshDatabase و وابستگی تست‌ها به هم.
  2. اجرای تست روی دیتابیس اصلی؛ همیشه phpunit.xml را چک کن.
  3. تست‌هایی که به ترتیب اجرا یا داده‌ی قبلی وابسته‌اند.
  4. تست‌نوشتن برای جزئیات پیاده‌سازی (نه رفتار)؛ رفتار را تست کن: «کاربر مهمان نمی‌تواند محصول بسازد».
  5. نادیده‌گرفتن تست fail شده و «بعداً درستش می‌کنم».
  6. تستی که به اینترنت واقعی یا ساعت واقعی وابسته است و گاهی قرمز می‌شود (Flaky).
  7. فقط تست «موفق» نوشتن و ندیدن خطاهای دسترسی و اعتبارسنجی.
  8. Mock بیش‌ازحد: اگر هر چیزی را Mock کنی، تست دیگر چیزی را ثابت نمی‌کند.
★

تمرین‌ها

تمرین ۱
  1. برای صفحه‌ی لیست محصولات یک Feature Test بنویس که محصول ناموجود را نشان ندهد (از inStock استفاده کن).
  2. تست بنویس که کاربر عادی نتواند به /admin برود (۴۰۳).
تمرین ۲
  1. یک کلاس CartCalculator بنویس و با Unit Test سه سناریو را بسنج: بدون تخفیف، تخفیف ۱۰٪، تخفیف ۱۵٪.
  2. یک مورد را عمداً خراب کن و ببین تست قرمز می‌شود.
تمرین ۳
  1. تست ثبت‌نام را بنویس: ثبت‌نام موفق، ایمیل تکراری و رمز کوتاه.
تمرین ۴
  1. برای پروژه‌ی فروشگاه یک تست با Http::fake برای بازگشت از درگاه بنویس (پرداخت موفق و ناموفق).
  2. یک تست با travel() بنویس که ثابت کند سفارش پرداخت‌نشده بعد از ۳۰ دقیقه لغو می‌شود.
تمرین ۵
  1. اعتبارسنجی شماره موبایل را با DataProvider و حداقل ۶ ورودی نامعتبر تست کن.
