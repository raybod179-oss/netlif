Accessor و Mutator: تبدیل داده هنگام خواندن و نوشتن

گاهی داده‌ی دیتابیس با چیزی که می‌خواهیم نمایش بدهیم یا ذخیره کنیم فرق دارد: قیمت را با جداکننده‌ی هزارگان می‌خواهیم، ایمیل را همیشه با حروف کوچک ذخیره می‌کنیم. Accessor هنگام «خواندن» و Mutator هنگام «نوشتن» یک ویژگی عمل می‌کند. در لاراول مدرن هر دو را با یک متد از نوع Attribute می‌نویسیم.

کدphp
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Casts\Attribute;
use Illuminate\Database\Eloquent\Model;

class Product extends Model
{
    // Accessor: $product->price_formatted
    protected function priceFormatted(): Attribute
    {
        return Attribute::make(
            get: fn () => number_format($this->price) . ' تومان',
        );
    }

    // هم Accessor هم Mutator روی ستون title
    protected function title(): Attribute
    {
        return Attribute::make(
            get: fn (string $value) => trim($value),
            set: fn (string $value) => mb_substr(trim($value), 0, 200),
        );
    }
}
نام‌گذاری

نام متد camelCase است ولی ویژگی با snake_case خوانده می‌شود: متد priceFormatted() ← $product->price_formatted. ویژگی‌ای که ستون واقعی ندارد (مثل priceFormatted) را اگر هنگام تبدیل به JSON هم بخواهی، در $appends بنویس.

Cast: نوع داده‌ی درست خودکار

کدphp
<?php

namespace App\Models;

use App\Enums\OrderStatus;
use Illuminate\Database\Eloquent\Model;

class Order extends Model
{
    protected function casts(): array
    {
        return [
            'paid_at'  => 'datetime',
            'is_gift'  => 'boolean',
            'meta'     => 'array',          // JSON ← آرایه
            'status'   => OrderStatus::class, // رشته ← Enum
            'password' => 'hashed',         // هنگام ذخیره خودکار هش می‌شود
        ];
    }
}

با cast، $order->paid_at یک شیء Carbon است (->diffForHumans()، ->format()) و $order->status یک Enum است؛ دیگر لازم نیست رشته‌ها را دستی مقایسه کنی.

Scope: کوئری‌های تکراری را نام بگذار

شرط‌هایی مثل «فقط محصولات موجود» را به‌جای تکرار در ده جا، یک‌بار با نام می‌نویسیم.

کدphp
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Builder;
use Illuminate\Database\Eloquent\Model;

class Product extends Model
{
    public function scopeInStock(Builder $query): Builder
    {
        return $query->where('stock', '>', 0);
    }

    public function scopePriceBetween(Builder $query, int $min, int $max): Builder
    {
        return $query->whereBetween('price', [$min, $max]);
    }
}

// استفاده (قابل زنجیره‌شدن):
// Product::inStock()->priceBetween(100000, 900000)->latest()->paginate(12);
Global Scope

اگر شرطی باید «همیشه» روی یک مدل اعمال شود (مثل فقط رکوردهای فعال)، Global Scope است. ولی با احتیاط: رفتار پنهان می‌سازد و خطایابی را سخت می‌کند. Soft Delete خودش یک Global Scope است.

مشکل N+1 و Eager Loading

تصور کن ۵۰ محصول را می‌گیری و در صفحه نام دسته‌ی هرکدام را نشان می‌دهی. اگر دسته‌ها را داخل حلقه بگیری، لاراول ۱ کوئری برای محصولات + ۵۰ کوئری برای دسته‌ها = ۵۱ کوئری می‌زند. به این می‌گویند N+1 و یکی از رایج‌ترین دلایل کندی سایت‌هاست.

کدphp
<?php

use App\Models\Product;

// ❌ N+1: هر بار $product->category یک کوئری جدید
$products = Product::all();
foreach ($products as $product) {
    echo $product->category->name;
}

// ✅ Eager Loading: فقط ۲ کوئری
$products = Product::with('category')->get();

// چند رابطه و رابطه‌ی تودرتو
$products = Product::with(['category', 'reviews.user'])->get();

// فقط بخشی از ستون‌ها (id را حتماً بگیر)
$products = Product::with('category:id,name')->get();

// شمارش و جمع بدون لود کردن همه‌ی رکوردها
$categories = App\Models\Category::withCount('products')->withSum('products', 'stock')->get();
// $category->products_count , $category->products_sum_stock
کدphp
<?php

namespace App\Providers;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Support\ServiceProvider;

class AppServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        // در حالت توسعه، هر Lazy Loading را خطا کن تا N+1 را همان لحظه بگیری
        Model::preventLazyLoading(! $this->app->isProduction());
    }
}
ابزار نمایشگر

با Laravel Debugbar یا Telescope تعداد کوئری‌های هر صفحه را ببین. اگر صفحه‌ی لیست محصولات ۵۰ کوئری می‌زند، یک جای کار می‌لنگد.

۵

Soft Delete: حذف نرم

به‌جای پاک‌کردن واقعی، فقط ستون deleted_at پر می‌شود. مثلاً برای سفارش‌ها و کاربران که ممکن است بعداً لازم شوند یا سابقه‌ی مالی دارند.

کدphp
<?php

// migration
Schema::table('products', function (Blueprint $table) {
    $table->softDeletes();
});

// model
use Illuminate\Database\Eloquent\SoftDeletes;

class Product extends Model
{
    use SoftDeletes;
}

// استفاده
$product->delete();                       // فقط deleted_at پر می‌شود
Product::withTrashed()->find($id);        // همراه حذف‌شده‌ها
Product::onlyTrashed()->get();            // فقط حذف‌شده‌ها
$product->restore();                      // برگرداندن
$product->forceDelete();                  // حذف واقعی و دائمی
یکتایی و Soft Delete

اگر ستونی مثل ایمیل unique است، رکورد حذف‌نرم‌شده هنوز آن مقدار را اشغال کرده است. این را در طراحی دیتابیس و Validation حتماً در نظر بگیر.

پردازش داده‌ی زیاد: chunk و cursor

کدphp
<?php

use App\Models\Order;

// ❌ همه را یک‌جا در حافظه می‌ریزد (با ۱ میلیون سطر، حافظه می‌ترکد)
// Order::all()->each(...)

// ✅ دسته‌دسته: هر بار ۵۰۰ تا
Order::where('status', 'paid')->chunkById(500, function ($orders) {
    foreach ($orders as $order) {
        // کاری روی هر سفارش
    }
});

// ✅ cursor: یکی‌یکی با حافظه‌ی کم
foreach (Order::where('status', 'paid')->cursor() as $order) {
    // ...
}

// when(): شرط اختیاری در کوئری بدون if اضافه
$products = Product::query()
    ->when(request('q'), fn ($q, $term) => $q->where('title', 'like', "%{$term}%"))
    ->when(request('min'), fn ($q, $min) => $q->where('price', '>=', $min))
    ->paginate(12);
chunk یا chunkById؟

اگر داخل حلقه همان ستونی را که فیلتر کرده‌ای تغییر می‌دهی (مثلاً status)، chunkById امن‌تر است؛ chunk ممکن است سطرها را جا بیندازد.

گام پروژه: بهینه‌سازی لیست فروشگاه

  1. در مدل Product یک Accessor به نام price_formatted و scope به نام inStock بساز.
  2. در ProductController@index از with('category:id,name') و inStock() استفاده کن و paginate(12) بزن.
  3. در AppServiceProvider خط preventLazyLoading را اضافه کن و اگر جایی خطا داد، رابطه را eager load کن.
  4. برای محصولات Soft Delete فعال کن و در پنل ادمین «سطل زباله» با onlyTrashed() و دکمه‌ی بازگردانی بساز.
۸

اشتباه‌های رایج

  1. فراموش‌کردن with() و N+1 (بزرگ‌ترین مشکل عملکرد).
  2. گرفتن all() روی جدول بزرگ.
  3. نوشتن منطق فرمت‌دهی داخل Blade به‌جای Accessor.
  4. انتخاب ستون‌ها با with('category:name') و فراموش‌کردن id (رابطه کار نمی‌کند).
  5. استفاده از Global Scope بدون مستندسازی و گیج‌شدن تیم.
★

تمرین‌ها

تمرین ۱
  1. برای مدل User یک Accessor به نام full_name بنویس (نام + نام‌خانوادگی).
  2. ستون settings از نوع JSON را با cast به array بخوان و بنویس.
تمرین ۲
  1. یک scope به نام popular بنویس که محصولات با بیش از ۱۰ فروش را برگرداند.
  2. کوئری جست‌وجو با when() برای نام، دسته و بازه‌ی قیمت بساز.
تمرین ۳
  1. صفحه‌ای بساز که ۵۰ محصول را با دسته‌شان نشان بدهد؛ یک‌بار با N+1 و یک‌بار با with. تعداد کوئری را مقایسه کن.
