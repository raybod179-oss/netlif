Event، Listener و Notification

کدی که هر اتفاق مهم را با یک خط اعلام می‌کند و کارهای جانبی را به Listenerها می‌سپارد، خواناتر و قابل‌توسعه‌تر است؛ این همان الگویی است که در پروژه‌ی مارکت‌پلیس استفاده می‌کنیم.

۱

چرا Event و Listener؟

وقتی سفارش پرداخت می‌شود باید چند کار انجام شود: ایمیل، پیامک، کم‌کردن موجودی، اطلاع به ادمین. اگر همه را داخل یک متد کنترلر بنویسی، کنترلر بزرگ و شکننده می‌شود. با Event فقط اعلام می‌کنی «OrderPaid اتفاق افتاد» و هر Listener مسئول یک کار می‌شود؛ کنترلر نمی‌داند چه کسانی گوش می‌دهند.

کشف خودکار

در لاراول جدید، Listenerهایی که در متد handle نوع Event را type-hint کرده‌اند، خودکار کشف می‌شوند و نیازی به ثبت دستی نیست. بررسی با php artisan event:list.

Observer: گوش‌دادن به رویدادهای مدل

کدbash

کدphp
<?php

namespace App\Observers;

use App\Models\Order;
use Illuminate\Support\Str;

class OrderObserver
{
    public function creating(Order $order): void
    {
        $order->number = 'RV-'.Str::upper(Str::random(8));   // شماره‌ی سفارش خودکار
    }

    public function updated(Order $order): void
    {
        if ($order->wasChanged('status')) {
            // وضعیت عوض شد؛ مثلاً Event بفرست
        }
    }
}
کدphp
<?php

namespace App\Models;

use App\Observers\OrderObserver;

}
Observer یا Event؟

Observer برای واکنش به «تغییر مدل» (created, updated, deleted). Event برای «اتفاق‌های کسب‌وکار» (سفارش پرداخت شد). کار مهم و پیچیده را در Observer پنهان نکن؛ خواندن کد سخت می‌شود.

Notification: یک پیام، چند کانال

کدbash
php artisan make:notification OrderPaidNotification
php artisan make:notifications-table && php artisan migrate   # برای کانال database
کدphp
<?php

namespace App\Notifications;

use App\Models\Order;
use Illuminate\Bus\Queueable;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Notifications\Messages\MailMessage;
use Illuminate\Notifications\Notification;

class OrderPaidNotification extends Notification implements ShouldQueue
{
    use Queueable;

    public function __construct(public Order $order) {}

    public function via(object $notifiable): array
    {
        return ['mail', 'database'];   // ایمیل + اعلان داخل سایت
    }

    public function toMail(object $notifiable): MailMessage
    {
        return (new MailMessage)
            ->subject('پرداخت سفارش شما تایید شد')
            ->greeting('سلام '.$notifiable->name)
            ->line('سفارش شماره‌ی '.$this->order->number.' با موفقیت پرداخت شد.')
            ->action('مشاهده‌ی سفارش', url('/orders/'.$this->order->id))
            ->line('از خرید شما ممنونیم.');
    }

    public function toArray(object $notifiable): array
    {
        return ['order_id' => $this->order->id, 'number' => $this->order->number];
    }
}
کدphp
<?php

// ارسال
$user->notify(new OrderPaidNotification($order));

// خواندن اعلان‌های داخل سایت (کانال database)
$unread = $user->unreadNotifications;       // خوانده‌نشده‌ها
$user->unreadNotifications->markAsRead();   // علامت خوانده‌شدن

برای ارسال پیامک یک «کانال سفارشی» می‌نویسیم؛ جزئیاتش را در درس ایمیل و پیامک می‌بینی.

تست Event و Notification

کدphp
<?php

namespace Tests\Feature;

use App\Events\OrderPaid;
use App\Models\Order;
use App\Models\User;
use App\Notifications\OrderPaidNotification;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Illuminate\Support\Facades\Event;
use Illuminate\Support\Facades\Notification;
use Tests\TestCase;

class OrderEventsTest extends TestCase
{
    use RefreshDatabase;

    public function test_event_is_dispatched(): void
    {
        Event::fake();
        $order = Order::factory()->create();

        OrderPaid::dispatch($order);

        Event::assertDispatched(OrderPaid::class);
    }

    public function test_user_is_notified(): void
    {
        Notification::fake();
        $user = User::factory()->create();
        $order = Order::factory()->create(['user_id' => $user->id]);

        $user->notify(new OrderPaidNotification($order));

        Notification::assertSentTo($user, OrderPaidNotification::class);
    }
}

Listener صف‌دار و امن در برابر تراکنش

Listener پیش‌فرض هم‌زمان اجرا می‌شود و پاسخ کاربر را کند می‌کند. کارهای کند (ایمیل، پیامک، تماس با API بیرونی) را با ShouldQueue به صف بفرست.

کدphp
namespace App\Listeners;

use App\Events\OrderPlaced;
use Illuminate\Contracts\Events\ShouldHandleEventsAfterCommit;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Queue\InteractsWithQueue;

class SendOrderConfirmation implements ShouldQueue, ShouldHandleEventsAfterCommit
{
    use InteractsWithQueue;

    public int $tries = 3;
    public array $backoff = [10, 60, 300];   // فاصله‌ی تلاش‌های دوباره (ثانیه)

    public function handle(OrderPlaced $event): void
    {
        $event->order->user->notify(new \App\Notifications\OrderConfirmed($event->order));
    }

    public function failed(OrderPlaced $event, \Throwable $e): void
    {
        logger()->error('order confirmation failed', ['order' => $event->order->id, 'error' => $e->getMessage()]);
    }
}
چرا ShouldHandleEventsAfterCommit؟

اگر Event را داخل DB::transaction بفرستی و Listener صف‌دار فوراً اجرا شود، ممکن است سفارش هنوز Commit نشده باشد و Worker آن را پیدا نکند (ModelNotFoundException). این Interface می‌گوید «بعد از Commit اجرا شو». برای Jobها هم dispatch(...)->afterCommit() همین کار را می‌کند.

در لاراول ۱۲ لیسنرها خودکار کشف می‌شوند: متد handle با Type-hint نوع Event کافی است و لازم نیست در AppServiceProvider ثبت‌شان کنی. فهرست را با php artisan event:list ببین.

کدphp
// جلوگیری از اجرا، بر اساس شرط
public function shouldQueue(OrderPlaced $event): bool
{
    return $event->order->total > 0;
}

// Subscriber: چند Listener یک موضوع در یک کلاس
use Illuminate\Events\Dispatcher;
class OrderEventSubscriber
{
    public function subscribe(Dispatcher $events): array
    {
        return [
            OrderPlaced::class    => 'onPlaced',
            OrderCancelled::class => 'onCancelled',
        ];
    }
    public function onPlaced(OrderPlaced $e): void { /* ... */ }
    public function onCancelled(OrderCancelled $e): void { /* ... */ }
}

کانال‌ها: Database، Broadcast و چند کانالی

یک Notification می‌تواند هم‌زمان با چند کانال بروید. کانال database برای «زنگوله‌ی اعلان» داخل سایت عالی است.

کدbash
php artisan make:notifications-table
php artisan migrate
php artisan make:notification OrderConfirmed
کدphp
class OrderConfirmed extends Notification implements ShouldQueue
{
    use Queueable;

    public function __construct(public Order $order) {}

    public function via(object $notifiable): array
    {
        // ترجیح کاربر را بخوان: همه ایمیل نمی‌خواهند
        return $notifiable->wants_email ? ['database', 'mail'] : ['database'];
    }

    public function toMail(object $notifiable): MailMessage
    {
        return (new MailMessage)
            ->subject('سفارش شما ثبت شد')
            ->greeting('سلام ' . $notifiable->name)
            ->line('سفارش شماره‌ی ' . $this->order->id . ' با موفقیت ثبت شد.')
            ->action('مشاهده‌ی سفارش', route('orders.show', $this->order));
    }

    public function toArray(object $notifiable): array
    {
        return ['order_id' => $this->order->id, 'text' => 'سفارش ' . $this->order->id . ' ثبت شد'];
    }
}
کدphp
// نمایش اعلان‌ها

$user->unreadNotifications->markAsRead();   // همه را خوانده کن

// ارسال بدون کاربر (مثلاً به ایمیل یک مهمان)
Notification::route('mail', 'guest@example.com')->notify(new OrderConfirmed($order));

الگوی طراحی: کی Event، کی Observer، کی مستقیم؟

وضعیتانتخابدلیل
اتفاقی که چند کار مستقل بعدش لازم دارد (ایمیل + انبار + آمار)Event + چند Listenerاضافه‌کردن کار جدید بدون دست‌زدن به کد قبلی
واکنش به ساخت/تغییر خود مدل (slug، لاگ، پاک‌کردن کش)Observerنزدیک مدل و بدون نیاز به فراخوانی دستی
کاری که باید حتماً هم‌زمان و با خطای فوری انجام شودفراخوانی مستقیم ServiceEvent منطق را پنهان می‌کند؛ برای قلب منطق مالی شفافیت بهتر است
اطلاع‌رسانی به کاربرNotificationکانال‌های متعدد، صف و قالب یکپارچه
  • Event را به‌صورت گذشته نام‌گذاری کن: OrderPlaced، نه PlaceOrder. یعنی «اتفاق افتاده»، نه «دستور».
  • فقط داده‌ی لازم را در Event بگذار (مدل یا شناسه). اگر Listener صف‌دار است، مدل‌ها با SerializesModels از دیتابیس دوباره خوانده می‌شوند.
  • منطق مالی حساس (کم‌کردن موجودی، ثبت تراکنش) را داخل Listener نگذار؛ در Service و داخل تراکنش انجام بده و فقط «اعلان‌ها و جانبی‌ها» را به Event بسپار.
  • برای دیباگ: Event::fake() در تست‌ها و php artisan event:list برای دیدن اتصال‌ها.
کدphp
// تست: بعد از ثبت سفارش، Event فرستاده شده و Notification رفته؟
Event::fake([OrderPlaced::class]);
$this->actingAs($user)->post('/checkout', $data)->assertRedirect();
Event::assertDispatched(OrderPlaced::class, fn ($e) => $e->order->user_id === $user->id);

Notification::fake();
$user->notify(new OrderConfirmed($order));
Notification::assertSentTo($user, OrderConfirmed::class);
۹

اشتباه‌های رایج

  1. ریختن همه‌ی منطق داخل یک Listener بزرگ؛ هر Listener یک کار.
  2. فراموش‌کردن ShouldQueue و کند شدن پاسخ کاربر.
  3. ارسال Event قبل از commit تراکنش (Listener داده‌ی ذخیره‌نشده را نمی‌بیند).
  4. وابستگی پنهان به ترتیب اجرای Listenerها.
  5. عدم تست؛ با Event::fake() می‌توانی ساده تست کنی.
  6. فرستادن Event داخل تراکنش و اجرای Listener صف‌دار قبل از Commit (راه‌حل: ShouldHandleEventsAfterCommit یا afterCommit()).
  7. گذاشتن منطق اصلی کسب‌وکار (مثل کم‌کردن موجودی) فقط داخل Listener صف‌دار؛ اگر Worker خاموش باشد، هیچ‌وقت انجام نمی‌شود.
  8. فراموش‌کردن جدول notifications (خطای جدول موجود نیست).

تمرین‌ها

تمرین ۱
  1. رویداد UserRegistered بساز و Listener‌ای که ایمیل خوش‌آمد بفرستد؛ سپس با Event::fake تست کن.
تمرین ۲
  1. Observer برای Product بنویس که هنگام creating اسلاگ را از عنوان بسازد.
تمرین ۳
  1. صفحه‌ی «اعلان‌های من» بساز که اعلان‌های database را نشان دهد و با کلیک خوانده‌شده کند.
تمرین ۴
  1. Event OrderPlaced بساز و سه Listener صف‌دار برایش بنویس: ایمیل تأیید، کم‌کردن موجودی (در پروژه‌ی فروشگاه)، و ثبت لاگ.
  2. کانال database را اضافه کن و صفحه‌ی «اعلان‌های من» با دکمه‌ی «خوانده شد» بساز.
تمرین ۵
  1. یک Subscriber برای رویدادهای سفارش بنویس و با event:list ثبت‌شدنش را ببین؛ سپس یک تست با Event::fake برایش بنویس.
