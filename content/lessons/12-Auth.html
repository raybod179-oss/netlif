۱

احرازِ هویت چیست و چرا

«احرازِ هویت» یعنی اثباتِ «کیستی» کاربر. Laravel این را با دو مفهوم انجام می‌دهد: guard (چطور وضعیتِ کاربر برای هر درخواست چک می‌شود) و provider (کاربرها از کجا خوانده می‌شوند).

Guard

پیش‌فرضِ وب، session است: بعد از ورود موفق، یک کوکیِ سشن با شناسه‌اش برایِ مرورگر صادر می‌شود و هر درخواستِ بعدی با همان سشن «کاربرش» را می‌شناسد.

Provider

پیش‌فرض Eloquent است با مدلِ App\Models\User. یعنی «کاربر» در جدولِ users است و Eloquent آن را برمی‌گرداند.

config/auth.php

تنظیماتِ guardها و providerها این‌جاست. وقتی پروژه‌هایِ پیشرفته‌تر (مثلِ admin جدا) می‌خواهی، همین‌جا guard اضافه می‌کنی.

یعنی کارِ اصلی فقط ساختنِ «ورود/خروج» است؛ بقیه‌ی امکانات از قبل در چارچوب آماده است.

از کجا ادامه می‌دهیم؟

فرمِ ثبت‌نامِ بخشِ ۱۰ کاربر می‌سازد (با هش‌کردنِ Hash::make). حالا آن کاربر باید بتواند «وارد» شود و بعدِ ورود «بماند». همه‌ی این‌ها همین‌جا است.

۲

روت‌ها و فرمِ ورود

مثلِ درسِ ۱۰، دو روت: نمایشِ فرم و پردازشِ فرم:

کدroutes/web.php
Route::get('/login', [AuthController::class, 'create'])->name('login');
Route::post('/login', [AuthController::class, 'store'])->name('login.store');
Route::post('/logout', [AuthController::class, 'logout'])->name('logout');

و فرمِ ورود — با همان سلاحِ درسِ ۱۰ (@csrf، old()، @error):

کدresources/views/auth/login.blade.php
<form method="POST" action="{{ route('login.store') }}">
    @csrf

    <label for="email">ایمیل</label>
    <input type="email" name="email" id="email" value="{{ old('email') }}">
    @error('email') <p class="field-error">{{ $message }}</p> @enderror

    <label for="password">رمز عبور</label>
    <input type="password" name="password" id="password">
    @error('password') <p class="field-error">{{ $message }}</p> @enderror

    <button type="submit">ورود</button>
</form>
چرا name('login')؟

زودتر می‌بینی: middlewareِ auth وقتی کاربرِ لاگین‌نکرده را می‌بیند، او را به همین «روتِ نام‌دارِ login» ریدایرکت می‌کند. بدونِ نامِ روت، middleware نمی‌داند کجا بفرستد.

۳

Auth::attempt و چرخه‌ی ورود

قلبِ ورود، متدِ Auth::attempt() است: مشخصات را می‌گیرد، کاربر را از provider پیدا می‌کند، هشِ رمز را با bcrypt چک می‌کند (پس هیچ‌وقت خودت Hash::check نزن) و در صورتِ تأیید، سشن را اصطلاحاً «لاگین» می‌کند:

کدAuthController.php
use Illuminate\Support\Facades\Auth;
use Illuminate\Validation\ValidationException;

public function store(Request $request): RedirectResponse
{
    $credentials = $request->validate([
        'email'    => ['required', 'email'],
        'password' => ['required'],
    ]);

    if (Auth::attempt($credentials)) {
        $request->session()->regenerate();      // جلویِ session fixation
        return redirect()->intended('dashboard');
    }

    throw ValidationException::withMessages([
        'email' => ['مشخصاتِ داده‌شده با سوابقِ ما مطابقت ندارد'],
    ]);
}
  • Auth::attempt([...]) فقط email/password لازم را می‌خواهد؛ بقیه‌ی کلیدها (مثلاً active => 1) شرطِ کوئری می‌شوند.
  • $request->session()->regenerate() یک «سشنِ تازه» می‌گیرد که حمله‌ی session fixation را خنثی کند — همیشه بعدِ ورود.
  • redirect()->intended('dashboard'): اگر کاربر قبلاً وسطِ کار به صفحه‌ای قفل‌شده رفته بود، به همان‌جا برمی‌گردد؛ وگرنه «dashboard».
  • خطایِ «مشخصات درست نیست» را نمی‌گذاری که صفحه بفهمد «ایمیلِ درست ولی پسوردِ غلط» — همین‌طور شناسیِ رمزی کمتر.
فرمِ ورود POST می‌شود ← validation + Auth::attempt → درست: regenerate + ریدایرکتِ intended / نادرست: پیامِ دقیقِ «ایمیل درست ولی رمز غلط»
۴

کاربرِ فعلی: Auth::user()

بعد از ورود، کاربرِ لاگین‌کرده را با چند فرمولِ مساوی می‌گیری:

کدPHP — هم‌ارزند
use Illuminate\Support\Facades\Auth;

$user = Auth::user();                      // کاربرِ فعلی (مدل User) یا null
$id   = Auth::id();                        // شناسه‌ی کاربرِ فعلی
$ok   = Auth::check();                     // true اگر لاگین باشد

// داخلِ بلید هم همین‌طور:
{{ auth()->user()->name }}                {{-- کمکِ سراسری auth() --}}
{{ $request->user()->email }}             {{-- از خودِ Request --}}
  • auth()->user() یک helperِ سراسری است که کوتاه‌تر از Auth::user() است و همان کار را می‌کند.
  • در متدِ کنترلر، $request->user() تمیزترین راه است (همان‌طور در درسِ ۱۱ در CheckRole دیده‌ای).
  • اگر لاگین نباشد، این‌ها به‌جای خطا فقط null می‌دهند. برایِ چکِ «لاگین هستی یا نه» از Auth::check() استفاده کن.
null کجای ذهن؟

رویِ روت‌هایی که auth middleware دارند، کاربرِ فعلی امن است؛ رویِ روتِ عمومی، اول Auth::check() را نکن، بلید را با @auth/@guest شرطی بکن (درسِ ۶).

۵

محافظتِ روت‌ها با auth

عینِ درسِ ۱۱: middlewareِ auth (aliasِ از کلاسِ Authenticate) روت را «فقط برایِ لاگین‌کرده‌ها» می‌کند و کاربرِ لاگین‌نکرده را به login ریدایرکت می‌کند:

کدroutes/web.php
Route::get('/dashboard', function () {
    // فقط کاربرِ لاگین‌کرده می‌رسد...
})->middleware('auth')->name('dashboard');

Route::get('/login', [AuthController::class, 'create'])->name('login');

// گروهِ تمامِ روت‌هایِ محافظت‌شده:
Route::middleware(['auth'])->group(function () {
    Route::get('/cart', [CartController::class, 'index'])->name('cart');
    // ...
});
  • آدرسِ ریدایرکت را می‌توانی با ->redirectGuestsTo('/login') در bootstrap/app.php تغییر دهی.
  • برعکس: middlewareِ guest فقط «لاگین‌نکرده‌ها» را رد می‌کند و لاگین‌کرده را به dashboard می‌فرستد — درِ ورود/ثبت‌نام.
  • حواست باشد: روتِ login باید بدونِ auth باشد (مهمان هم باید بهش برسد!)
قفلِ سمتِ مرورگر کافی نیست

مخفی‌کردنِ لینکِ «ورود» با @guest امنیت نمی‌آورد؛ «امنیت» یعنی خودِ روت مثلِ بالا middleware داشته باشد. پنهان‌کاریِ بلید فقط تجربه‌ی کاربری است.

۶

@auth و @guest در بلید

دو دستورِ اختصاصی برایِ «لاگین است / نیست» در بلید:

کدBlade
@auth
    <p>خوش آمدی، {{ auth()->user()->name }}!</p>
@endauth

@guest
    <a href="{{ route('login') }}">ورود</a>
    <a href="{{ route('register') }}">ثبت‌نام</a>
@endguest

این دو، مکملِ هم‌اند: @auth یعنی «کاربرِ لاگین‌کرده دارد»، @guest یعنی «ندارد». برایِ بخشِ سربرگِ فروشگاه، این‌طوری چیزِ درست را نشان می‌دهیم:

@auth  →  «خروج» + نامِ کاربر | @guest  →  «ورود» + «ثبت‌نام»
و درِ @can؟

گیتس (درسِ ۹ همین بخش) هم دستورِ مخصوص خودش را دارد: @can('manage-products') — فوراً بعدش.

۷

خروج و امنیتِ سشن

خروجِ کامل سه‌گام است — هر سه مالِ «سشن» است، نه فقط یکی:

کدAuthController.php
public function logout(Request $request): RedirectResponse
{
    Auth::logout();                      // ۱) حالتِ لاگین را بردار

    $request->session()->invalidate();   // ۲) داده‌هایِ سشن را بسوزان

    $request->session()->regenerateToken();  // ۳) توکنِ CSRF را تازه کن

    return redirect('/');
}
  • Auth::logout() خودش وضعیتِ کاربر را برمی‌دارد.
  • ولی برایِ امنیتِ کامل، سشن باید باطل (داده‌اش پاک) و توکنِ CSRF تازه شود — وگرنه توکنِ قدیمیِ صفحه‌ی قبلی از کار می‌افتد و فرم بعدی خطای ۴۱۹ می‌دهد.
  • میان‌بندِ auth.session هم هست که سشنِ دستگاه‌هایِ دیگر را باطل کند — خارجِ چارچوبِ دوره.
۸

استارتر کیت‌های رسمی

حواست باشد: در نسخه‌هایِ جدیدِ Laravel (۱۲ و ۱۳) دیگر «Breeze» توصیه نمی‌شود. به‌جایش Laravel «استارتر کیت»های رسمی دارد که کلِ سیستمِ احرازِ هویت را با فرم، validator و پنلِ پروفایل به‌طورِ کامل اسکلت می‌کنند — با laravel new همان لحظه انتخاب می‌شوند:

Livewire

نزدیک‌ترینِ انتخاب به این دوره — بلید + Livewire + Tailwind. برایِ تیم‌هایِ PHP.

React / Vue / Svelte

با Inertia (SPA درکنارِ روتینگِ کلاسیکِ سمتِ سرور). مدرن‌ترینِ گزینه‌ها.

موتورِ پشتی: Fortify

همه‌ی کیت‌ها روت/postها و controllerها را از Fortify دارند — همون تمرینِ دستیِ ما در این بخش، ولی آماده.

پس در یک پروژه‌ی واقعی، به‌جایِ «نصبِ Breeze»، یکی از کیت‌ها را با laravel new انتخاب می‌کنی؛ چون خودِ کدِ auth داخلِ پروژه‌ات است، می‌توانی بعداً همه‌چیز را آن‌طور که این‌جا یاد گرفتی عوض کنی.

چرا این درس دستیِ نوشتن را یاد می‌دهد؟

چون کیت‌ها بخش زیادی از کد را از پیش نوشته‌اند. وقتی خودت Auth::attempt را دیدی، می‌فهمی آن‌ها چه می‌کنند — و اگر روزی کیتِت جواب نداد، بلدی کجا را نگاه کنی.

۹

Gate ساده با Gate::define

تا الان «کسی است» را داشتیم (auth). حالا «اجازه‌ی آن کار را دارد؟» — این شد «authorization». ساده‌ترین راهِ قابلِ طراحی، Gate است: یک قاعده برایِ یک توانایی، که اول User و بقیه‌ی پارامترها را می‌گیرد:

کدApp/Providers/AppServiceProvider.php — متد boot
use App\Models\User;
use Illuminate\Support\Facades\Gate;

public function boot(): void
{
    Gate::define('manage-products', function (User $user) {
        return $user->role === 'admin';
    });
}

و مصرفِ آن در کنترلر یا بلید:

کدPHP — authorize در کنترلر
use Illuminate\Support\Facades\Gate;

public function destroy(Product $product): RedirectResponse
{
    Gate::authorize('manage-products');   // اگر اجازه نباشد → 403

    $product->delete();
    return back();
}
کدBlade —نمایشِ شرطی
@can('manage-products')
    <a href="{{ route('products.create') }}">افزودنِ محصول</a>
@endcan
  • Gate::authorize('name', $model) اگر رد شود خودش ۴۰۳ برمی‌گرداند؛ قبولِ کنترلیِ دستی با Gate::allows/denies.
  • برایِ قوانینِ مربوط به یک مدل (مثلِ «این محصول را فقط صاحبش ویرایش کند») Policy بهتر است — در پروژه‌ی پایانی می‌بینی‌اش.
  • @can('manage-products') در بلید فقط لینک را مخفی می‌کند؛ امنیتِ واقعی همچنان با Gate در کنترلر است. (لینکِ مخفی + روتِ بی‌دروازه = امنیتِ صفر!)
چرا Gate بهتر از چکِ دستی است؟

با $request->user()->role اگر کاربر لاگین نکرده باشد، خطا می‌گیری. ولی Gate خودش برایِ کاربرِ لاگین‌نکرده false برمی‌گرداند — بدونِ کرش. این نکته‌ی خیلی مهمی در auth است.

۱۰

گام پروژه: لاگین + نقش admin

تکمیلی: فروشگاهِ واقعی، با ورود و پنلِ مدیریت

سه کار: (۱) کاربران «نقش» بگیرند (admin/customer)، (۲) ورودِ واقعی کار کند، (۳) پنلِ /admin که در درسِ ۱۱ ساختیم، پذیرفته‌ای فقط admin.

  1. ستونِ role: یک migration اضافه کن (داخلِ جدولِ کاربران، پیش‌فرضِ customer):
$ php artisan make:migration add_role_to_users_table --table=users INFO Migration [database/migrations/…_add_role_to_users_table.php] created successfully.
کدداخلِ migration — متد up
Schema::table('users', function (Blueprint $table) {
    $table->string('role')->default('customer')->after('email');
});
  1. یک admin بساز: با ابتدایِ پروژه‌ات یا Tinker: User::where('email', 'admin@shop.test')->update(['role' => 'admin']).
  2. روتِ مدیریت را قفل کن — الآن که ورود داریم، درسِ ۱۱ جواب می‌دهد:
کدroutes/web.php
Route::middleware(['auth', 'check-role:admin'])->group(function () {
    Route::get('/admin', [DashboardController::class, 'index'])->name('admin.dashboard');
    // ... و هر روتِ مدیریتیِ دیگر
});
  1. دستورهایِ بلید: درِ سربرگِ سایت، @auth/@guest؛ و فقط به admin لینکِ خوبِ «مدیریت» را بده: @can('manage-products') <a href="{{ route('admin.dashboard') }}">مدیریت</a> @endcan (اگر Gateِ درسِ ۹ را بپذیرفت).
  2. تکمیلِ ثبت‌نامِ بخشِ ۱۰: درِ store() به‌جایِ redirect به خودِ ثبت، کاربرِ تازه را ثبت کن و بفرستش به صفحه‌ی login.
ترتیبِ middleware مهم است

['auth', 'check-role:admin'] — اولِ auth (لاگین لازم است)، بعدِ check-role (نقشِ admin). برعکسِ این ترتیب، مهمانِ بی‌نقش به‌جای «برو لاگین کن» خطای ۴۰۳ می‌گیرد. ترتیبِ middleware درسِ ۱۱ را یادت نرود.

۱۱

تمرین‌ها؛ حالا نوبت توست!

تمرین ۱: ورودِ پاک
  1. فرمِ ورود + Auth::attempt + regenerate را پیاده کن.
  2. با ایمیلِ درست/پسوردِ غلط بفرست: باید فقط پیامِ «مشخصات مطابقت ندارد» ببینی — نه اینکه بگوید کدام‌اش غلط است.
  3. بعدِ لاگین، به سربرگ برو که حالتِ @auth نامِ کاربر را نشان بدهد.
تمرین ۲: فقط manager می‌تواند حذف کند
  1. یک Gate به اسمِ delete-product تعریف کن که نقشِ manager یا admin را قبول کند.
  2. درِ destroy() صداش کن تا مدیرِ بی‌اجازه ۴۰۳ بگیرد.
  3. با @can('delete-product') دکمه‌ی حذفِ فقطِ متعلقِ مجازها را نشان بده.
چالش

یک «پیش‌گشت» بساز: وقتی کاربرِ لاگین‌نکرده به /cart می‌رود، بعدِ لاگین باید دقیقاً همان /cart را ببیند، نه dashboard. راهنما: خودِ redirect()->intended() این کار را با middlewareِ auth انجام می‌دهد — بعدِ لاگین، «مقصدِ ذخیره‌شده» را ببین.

چیزی که از این بخش توی ذهنت بماند

  1. guard=چطور (سشن)، provider=کجا (users). همه‌ی ورود به دو متدِ Auth::attempt و Auth::logout ختم می‌شود.
  2. بعدِ ورود: session()->regenerate()؛ بعدِ خروج: logout + invalidate + regenerateToken.
  3. کاربرِ فعلی: auth()->user() / $request->user() — رویِ روتِ محافظت‌شده امن است.
  4. روتِ محافظت‌شده فقط با middleware: ->middleware('auth')؛ مهمان‌ها با guest.
  5. @auth/@guest UI است، auth و Gate امنیت است — مرز را نگه دار.
  6. در Laravel ۱۳ Breeze legacy است؛ کیتِ فعلی → Livewire / React / Vue (Fortify) با laravel new.
  7. Gate یعنی قاعده‌ی authorize برایِ «توانایی»؛ @can فقط نمایش است.
مطالعه‌ی بیشتر (انگلیسی): آشنایی با Authentication — کاربرِ فعلی: Auth::user، محافظتِ روت‌ها با auth، ورودِ دستی: Auth::attempt، خروج و امنیتِ سشن، استارتر کیت‌ها و Fortify و نوشتنِ Gate.
