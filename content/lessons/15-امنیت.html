امنیت پایه‌ی وب

این درس چهار نکته‌ای را می‌پوشاند که امنیت را از «اتفاقیِ بد» به «قاعده‌ی همیشگی» تبدیل می‌کنند. اگر این پنج ریسک را بشناسی — XSS، SQL Injection، CSRF و Brute-Force — نیمه‌ی بزرگی از باگ‌های امنیتیِ رایج را در طول عمر حرفه‌ای‌ات حذف کرده‌ای.

۱

چرا امنیت؟ نقشِ فریم‌ورک

هر درخواستی که به سایتِ تو می‌رسد از مرورگرِ «یک غریبه» می‌آید. آن غریبه می‌تواند پیامِ متنی، اسکریپت، و حتی فایلِ مخرب را بفرستد. «امنیتِ وب» یعنی اطمینان از اینکه خروجیِ سایت فقط همان چیزی را اجرا/نمایش می‌دهد که تو، نه چیزی که مهاجم، خواسته است.

XSS

تزریقِ کدِ Java­Script به داخلِ خروجیِ HTML — ربودنِ سشن یا جعلِ نمایش.

SQL Injection

تزریقِ دستورِ SQL از طریقِ ورودیِ کاربر برایِ خواندن/تخریبِ دیتابیس.

CSRF

فرستادنِ درخواست از طرفِ کاربرِ لاگین‌کرده به‌صورتِ ناخواسته (مثلِ فرمِ جعلی).

Brute-Force

حدسِ زدنِ رمز با هزاران تلاشِ خودکار — مهار با Rate Limiting.

خبرِ خوب: «بسیاری از این حملات را خودِ Laravel، به‌صورتِ پیش‌فرض مهار می‌کند». تو فقط باید بدانی دقیقاً کجا (و چرا) این محافظت فعال است تا آن را نشکنی.

تلفیقِ فصل‌ها

امنیت در چهار لایه پیش می‌آید: امنیتِ خروجی ({{ }})، امنیتِ کوئری (Eloquent)، امنیتِ درخواست (csrf و validation) و امنیتِ دسترسی (middleware و auth). هر لایه کارِ خودش را دارد.

۲

XSS و اکسکیپِ خودکار {{ }}

فرض کن یک محصول به اسمِ این می‌سازد:

کدورودیِ کاربر (نامِ محصول)
<script>alert('hacked')</script>

اگر این رشته را «عهدِ خام» داخلِ HTML چاپ کنی، مرورگر آن را اجرا می‌کند — این یعنی XSS. سلاحِ بلید، دستورِ {{ }} است که به‌صورتِ خودکار متن را «اکسکیپ» (escape) می‌کند؛ یعنی کاراکترهایِ <، > و... را به معادلِ HTML تبدیل می‌کند تا مرورگر به‌جایِ اجرا، فقط نمایش دهد:

کدBlade — امن
{{ $product->name }}
{{-- خروجی: <script>alert('hacked')</script> --}}
{{-- یعنی به‌صورتِ متنِ خام نمایش داده می‌شود، اجرا نمی‌شود --}}
خطرناک — این را ننویس
{!! $product->name !!} — خروجیِ خام بدونِ اکسکیپ. مگر اینکه خودت مطمئن باشی (مثلاً HTMLِ داخلیِ بومی‌شده توسط خودِ ادمین)؛ برایِ ورودیِ کاربر‌ها هرگز.
  • پس یادت بماند: {{ }} امن است، {!! !!} امن نیست. همیشه از {{ }} استفاده کن.
  • helperِ e($string) همان اکسکیپ را در PHPِ خالص انجام می‌دهد؛ در Blade فقط {{ }} لازم است.
  • حواست به attributeها هم باشد: <img src="{{ $url }}"> — خودِ {{ }} از تزریقِ attribute هم جلوگیری می‌کند.
بلید که نمی‌پرسی؟

در Blade، متغیرها خودکار ایمن چاپ می‌شوند (یعنی HTML-special-character ها تبدیل می‌شوند)؛ پس برایِ امنیت کارِ اضافه لازم نیست: همان {{ $value }} یا e($value) کافی است.

۳

SQL Injection و placeholder

حالا ببینیم چرا باید کوئری را دستی بنویسیم و به Query Builder تکیه نکنیم. اگر ورودیِ کاربر را مستقیم در SQL بچسبانی، خطرناک است:

خطرناک — تزریقِ SQL
DB::select("SELECT * FROM products WHERE name LIKE '%$term%'");
مثلاً اگر کاربر این را بفرستد: ' OR 1=1 --، ممکن است کلِ جدول را نشان بدهد یا حتی پاک کند. این یعنی SQL Injection، یکی از جدی‌ترین خطرهای وب.

سلاحِ پیش‌فرضِ Laravel: Query Builder و Eloquent، تمامِ مقادیر را از طریقِ «پارامترِ مرجع» (placeholder/prepared statement) می‌بندند. یعنی مقدار به‌صورتِ داده ارسال می‌شود، نه به‌صورتِ بخشی از دستور:

کدPHP — امن (جایگزینِ همان کوئری)
// Query Builder — امن
$products = DB::table('products')
    ->where('name', 'like', "%{$term}%")
    ->get();

// Eloquent — امن
$products = Product::where('name', 'like', "%{$term}%")->get();

// حتی درِ whereRaw هم باید ? بگذاری:
$products = DB::table('products')
    ->whereRaw('price > ? AND name LIKE ?', [$min, "%{$term}%"])
    ->get();
  • تا وقتی که از متدهایِ عادیِ Builder استفاده می‌کنی، مقادیر همیشه placeholder می‌شوند — امن.
  • اگر مجبور شدی whereRaw یا orderByRaw بزنی، مقادیرِ کاربر را هرگز بدونِ ? نگذار.
  • ترتیبِ ستون‌ها (orderBy/groupBy از ورودی) را همیشه با لیستِ سفیدِ از پیشِ تعریف‌شده چک کن.
ورودیِ مخرب
' OR 1=1 --
رشته‌ای که درِ SQLِ خام، «همه» را می‌فرستد.
با placeholder
به‌عنوانِ «مقدارِ رشته» بسته می‌شود: کاراکترهایِ تزریقی اجرا نمی‌شوند.
۴

CSRF و @csrf

تصور کن کاربرِ لاگین‌کرده واردِ یک سایتِ شیطانی شده که فرمِ جعلی دارد و «رویِ دکمه‌ی دیدنِ جایزه» می‌فرستد POST به /products/1 (همان روتِ حذفِ محصولاتِ تو). اگر تو سشنِ کاربر را بدونِ تأیید می‌پذیرفتی، محصولِ او ناخواسته حذف می‌شد. به این حمله می‌گویند CSRF (Cross-Site Request Forgery).

مقابلش چه کسی؟ میان‌افزارِ PreventRequestForgery که در گروهِ web فعال است و روی همه‌ی درخواست‌هایِ POST/PUT/PATCH/DELETE توکنِ CSRF را چک می‌کند. اگر توکن نباشد یا غلط باشد، خطای 419 برمی‌گردد:

کدBlade — درِ فرم
<form method="POST" action="{{ route('products.store') }}"
      enctype="multipart/form-data">
    @csrf
    <input type="text" name="name">
    <button type="submit">ذخیره</button>
</form>
  • @csrf یک <input type="hidden" name="_token"> تولید می‌کند که مقدارش همان توکنِ سشنِ کاربر است.
  • توکن با سشنِ مرورگرِ همان کاربر جفت است؛ سایتِ یک‌دیگری نمی‌تواند بسازدش.
  • اگر با AJAX فایل یا داده می‌فرستی، توکن را درِ هدرِ X-CSRF-TOKEN بگذار (مثلِ Meta تگِ استاندارد).
  • رایج‌ترین «خطایِ بی‌ضررِ مبتدی» هم این‌جاست: صفحه‌ی 419 Page Expired معمولاً یعنی «@csrf را جا کردی» یا سشنِت (مثلاً بعدِ logout) باطل شده است.
به‌خصوص برایِ روتِ api

روت‌هایِ API (گروهِ api) چون توکن می‌گیرند، به کوکی و سشن نیازی ندارند. ولی روت‌هایِ وب (گروهِ web) با @csrf محافظت می‌شوند.

۵

Rate Limiting با throttle

حملاتِ Brute-Force یعنی «یک آدرسِ IP، هزاران بار درخواستِ رمز حدس می‌زند». با Rate Limiting محدودش می‌کنیم: «در هر دقیقه فقط ۵ تلاشِ ورود از یک IP». اول یک «لیمیترِ نام‌دار» تعریف می‌کنیم — این کد داخلِ متدِ boot() در فایلِ app/Providers/AppServiceProvider.php می‌نشیند (نه در bootstrap/app.php):

کدapp/Providers/AppServiceProvider.php
use Illuminate\Cache\RateLimiting\Limit;
use Illuminate\Http\Request;
use Illuminate\Support\Facades\RateLimiter;

RateLimiter::for('login', function (Request $request) {
    return Limit::perMinute(5)->by($request->ip());
});

// یک لیمیترِ عمومی برایِ api (مثلِ پیش‌فرضِ پروژه): 
RateLimiter::for('api', function (Request $request) {
    return Limit::perMinute(60)
        ->by($request->user()?->id ?: $request->ip());
});

و بعد رویِ روتِ ورود، middlewareِ throttle:نام-لیمیتر را می‌گذاریم:

کدroutes/web.php
Route::post('/login', [AuthController::class, 'store'])
    ->middleware('throttle:login')->name('login.store');

// یا بدونِ لیمیترِ آینده، مستقیم: حداکثر ۱۰ درخواست درِ هر دقیقه
Route::get('/reports-export', function () { /* ... */ })
    ->middleware('throttle:10,1');
GET http://localhost:8000/login , POST /login → پس ازِ ۵ تلاشِ ناموفق: HTTP/1.1 429 Too Many Requests Retry-After: 60
  • throttle:نام لیمیترِ نام‌داری را صدا می‌زند که خودت تعریف کرده‌ای؛ throttle:10,1 یعنی «۱۰ تلاش درِ ۱ دقیقه» بدونِ تعریفِ جداگانه.
  • پاسخِ 429 یعنی از حد رد شده‌ای؛ می‌توانی با ->response() درِ لیمیتر، پیام/صفحه‌ی دلخواه بدهی.
  • برایِ سبدِ خرید یا جستجو هم همین الگو را بگذار — اما با حدِ بالاتر.
throttle و ورودِ ناموفق

فقط ۵ بار درِ دقیقه به POST /login اجازه می‌دهیم؛ همین یک خط، حملاتِ رمزِ خودکارِ ساده را عملاً می‌بندد.

۶

APP_DEBUG و محیطِ تولید

اگر APP_DEBUG=true باشد، هر خطا یک صفحه‌ی کاملِ دیباگ با مسیرِ فایل، محیطِ PHP، متغیرهایِ ENV (و گاهی حتی رمزِ دیتابیس) نشان می‌دهد. درِ یک سایتِ زنده این یعنی «اطلاعاتِ حساس به غریبه» — همان‌طور که درِ فصلِ ۱ .env را دیدیم:

کد.env — محلی (توسعه)
APP_NAME="فروشگاهِ کوچک"
APP_ENV=local
APP_DEBUG=true
کد.env — تولید (هاست)
APP_NAME="فروشگاهِ کوچک"
APP_ENV=production
APP_DEBUG=false
  • درِ production به‌جایِ جزئیاتِ خطا، یک صفحه‌ی عمومی‌تر نشان داده می‌شود (و خطا هنوز درِ storage/logs/laravel.log ثبت می‌شود).
  • اگر خطایی را نتوانستی پیدا کنی، برگردِ local (و بعدِ دیباگ دوباره خاموشش کن).
  • ضمناً APP_KEY باید با php artisan key:generate منحصربه‌فرد باشد.
امنیتِ .env خودت

فایلِ .env نباید هیچ‌وقت درِ GIT یا پوشه‌ی public باشد؛ gitignore از پیشِ لاراوَل آن را حذف کرده است. اگر پشتِ یک هاست بخواهی deploy کنی، از php artisan config:cache استفاده کن.

۷

Route::resource و only/except

نکته‌ی کم‌دیده‌شده: هر متدِ resource که رها می‌کنی یک «سطحِ حمله» و یک «سوراخِ احتمالی» است. اگر صفحه‌ای فقط خواندنی است (مثلِ صفحه‌ی عمومی‌ِ محصولات) چرا روتِ destroy برایش بگذاری؟ با only فقط آنچه لازم است را باز کن، و با except آنچه را نمی‌خواهی حذف کن:

کدroutes/web.php
// فقط index و show (بدونِ create/store/update/delete)
Route::resource('products', ProductController::class)
    ->only(['index', 'show']);

// همه‌ی resource، به‌جزِ destroy (مثلاً صفحه‌ی عمومی)
Route::resource('categories', CategoryController::class)
    ->except(['destroy']);

نتیجه: روتِ DELETE products اصلاً ثبت نمی‌شود و ۴۰۴ می‌دهد؛ اگر سراغش بروی هم چیزی برایِ حمله نیست. همین قانون ساده، «سطحِ حمله» را کوچک می‌کند — اصلِ «کمترین امتیاز/حداقلی بودن» در امنیت.

کدروت‌هایِ Created شده
GET      /products             → products.index
GET      /products/{product}   → products.show
// هیچ POST / PUT / DELETE ای ثبت نشده است.
  • بقیه‌ی متدهایِ resource را حذف کن؛ لازم نیست همه باز باشند. middleware را با ->only()->middleware() روی همان متدهایِ لازم بگذار.
  • برایِ جفت‌کردنِ resource و auth: Route::resource('products', ...)->only([...])->middleware('auth').
۸

سطوحِ امنیتیِ بیشتر: Mass Assignment

ولی یک اشتباهِ رایج، کلِ امنیتِ فرم را از بین می‌برد: وقتی کلِ ورودی را مستقیم به create() می‌دهی (Mass Assignment). با create($request->all()) هر فیلدی که کاربر بفرستد ذخیره می‌شود — حتی role یا is_verified که نباید از سمتِ کاربر پر شوند:

خطرناک
User::create($request->all()); — راه‌حل: روی مدل مشخص کن کدام فیلدها مجازند، با #[Fillable('name', 'email', 'password')].
کدapp/Models/User.php
// فقط این ستون‌ها قابلِ پر شدن از mass-assignment هستند
protected $fillable = ['name', 'email', 'password'];

// بقیه (مثلِ role) را باید به‌صرفِ کدِ خودت ست کنی:
$user = User::create(['name' => ..., 'email' => ..., 'password' => Hash::make(...)]);
$user->role = 'customer';   // درِ کدِ خودت — نه از ورودیِ کاربر
  • $fillable (لیستِ سفید) یا $guarded (لیستِ سیاه) — حداقلِ یکی لازم است.
  • هیچ‌وقت $request->all() را مستقیم به create() نده؛ همیشه فیلدهایِ مشخص را جدا کن یا از validated() (فصلِ ۱۰) استفاده کن.
  • این همان دلیلی است که قبلاً گفتیم: «جلوگیریِ لایه‌ی محدودکردن با fillable».
۹

گام پروژه: سخت‌کردنِ فروشگاه

تکمیلی: فروشگاهِ مقاوم‌شده

پنج‌گامِ ساده ولی حرفه‌ای که فروشگاهِ تمرینیِ تو را به «سایتِ واقعی» نزدیک می‌کند:

  1. اکسکیپ: درِ تمامِ بلیدها، مطمئن شو هرجایِ کاربر می‌بینند {{ }} است و هیچ‌جا {!! !!} با داده‌ی کاربر نیست.
  2. راه‌حل: اگر واقعاً کوئریِ خام لازم داری، همیشه از Query Builder استفاده کن و ورودی را با ? به‌جای درجِ مستقیم در رشته پاس بده (نه whereRaw با رشته‌سازی).
  3. CSRF: همه‌ی فرم‌هایِ POST/PUT/DELETE @csrf داشته باشند؛ فرمِ حذفِ محصول را با @method('DELETE') درست کن.
  4. throttle: برایِ POST /login لیمیترِ login (5 درِ دقیقه) را تعریف و وصل کن.
  5. محیط: اگر جایی deploy کردی، APP_ENV=production و APP_DEBUG=false را بگذار و config:cache بزن.
  6. resource: صفحه‌ی عمومیِ محصولات را با ->only(['index','show']) محدود کن؛ پنلِ مدیریت را با auth و only/except.
ادامه‌ی راه

درِ بخشِ آخر (پروژه‌ی پایانی)، همه‌ی این‌ها رویِ فروشگاه یکجا پیاده می‌شود؛ پس هر کدام را که الان جا گذاشتی، درِ پروژه برمی‌گردی بهش.

۱۰

تمرین‌ها؛ حالا نوبت توست!

تمرین ۱: تستِ XSS
  1. یک محصول با نامِ <script>alert(1)</script> بساز (با seed یا فرم).
  2. درِ بلید چک کن که «خروجی» به‌صورتِ متن نمایش داده می‌شود و هیچ پاپاپی بالا نمی‌آید.
  3. اگر با {!! !!} تست می‌کردی چه می‌شد؟ (بعدش دوباره به {{ }} برگرد.)
تمرین ۲: تزریقِ بی‌اثر
  1. درِ فرمِ جست‌وجو، مقدارِ ' OR 1=1 -- را وارد کن.
  2. ببین Query Builder همان «صفر نتیجه» یا «نتیجه‌ی عادی» را برمی‌گرداند — نه تخریب و نه لیستِ کامل.
  3. یک نسخه‌ی whereRawیِ بدونِ placeholder بساز و ببین چقدر راحت هک می‌شود؛ بعد حذفش کن.
تمرین ۳: ورودِ محافظت‌شده
  1. لیمیترِ login با Limit::perMinute(5) بساز و به روتِ ورود وصل کن.
  2. ۶ بار پشت‌سرهم «رمزِ غلط» وارد کن؛ تلاشِ ۶ام باید 429 بدهد.
  3. برایِ جست‌وجوی محصول هم لیمیترِ perMinute(30) اضافه کن.
چالش

درِ فرمِ «حذفِ محصول» یک حمله‌ی CSRF شبیه‌سازی کن: یک صفحه‌ی HTMLِ ساده درِ پوشه‌ی دیگری باز کن که <form action="http://localhost:8000/products/1" method="POST"> با یک دکمه‌ی بی‌ضرر دارد. رویِ Deleteِ محصولِ واقعی، بدونِ @csrf چه اتفاقی می‌افتد؟ (راهنما: 419)

چیزی که از این بخش توی ذهنت بماند

  1. XSS: برایِ داده‌ی کاربر همیشه {{ }} یا e() (هر دو خودکار escape می‌کنند). {!! !!} فقط برایِ داده‌ای که خودت ساخته‌ای و کاملاً مطمئنی.
  2. SQL Injection: با Builder یا Eloquent کار کن و ورودی را با ? پاس بده؛ اگر ناچار به کوئریِ خام شدی، هرگز رشته‌سازی نکن.
  3. Brute-Force مهار می‌شود: throttle:login برایِ ورود (۵ درِ دقیقه)؛ 429 یعنی محدود شده‌ای.
  4. CSRF: درِ گروهِ web توکن را خودکار چک می‌کند؛ فقط یادت بماند @csrf در فرم بگذاری، وگرنه ۴۱۹ می‌گیری.
  5. تولید: APP_DEBUG=false؛ درِ محلی true. صفحه‌ی خطایِ جزئیات، دانشِ حمله به مهاجم می‌دهد.
  6. متدهایِ اضافه را حذف کن: Route::resource(...)->only([...]) به‌جایِ except + middleware.
  7. Mass Assignment: با #[Fillable(...)] مشخص کن چه فیلدهایی مجازند؛ create($request->all()) ناامن است.
مطالعه‌ی بیشتر (انگلیسی): Laravel Security — Blade و escape کردنِ خروجی - Query و prepared statements — CSRF Protection — Rate Limiting — و Mass Assignment.
