۱

چرا صف؟

وقتی کاربر سفارش می‌دهد، چند کار لازم است: ایمیل رسید، پیامک، ساخت فاکتور PDF، به‌روزرسانی انبار. اگر همه را همان لحظه (هم‌زمان) انجام بدهی، کاربر ۱۰ ثانیه منتظر می‌ماند و اگر سرویس ایمیل کند باشد، کل سفارش خراب می‌شود. صف (Queue) یعنی کارهای سنگین را در یک «لیست انتظار» می‌گذاریم و یک پروسه‌ی جدا (Worker) آن‌ها را بعداً انجام می‌دهد؛ پاسخ به کاربر فوری است.

Driverکاربرد
syncفوری و بدون صف؛ فقط برای تست
databaseپیش‌فرض و ساده؛ بدون نصب چیز اضافه (برای شروع عالی است)
redisسریع‌تر و مناسب ترافیک بالا
کدbash
# در .env
QUEUE_CONNECTION=database

php artisan migrate          # جدول‌های jobs و failed_jobs
php artisan queue:work       # شروع Worker (باید همیشه روشن باشد)
۲

ساخت و ارسال Job

کدbash
php artisan make:job SendOrderReport
کدphp
<?php

namespace App\Jobs;

use App\Models\Order;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;
use Illuminate\Support\Facades\Log;
use Throwable;

class SendOrderReport implements ShouldQueue
{
    use Queueable;

    public int $tries = 3;        // حداکثر ۳ بار تلاش
    public int $timeout = 60;     // هر تلاش حداکثر ۶۰ ثانیه

    public function __construct(public Order $order) {}

    // فاصله‌ی بین تلاش‌های ناموفق (ثانیه): ۱۰، ۶۰، ۳۰۰
    public function backoff(): array
    {
        return [10, 60, 300];
    }

    public function handle(): void
    {
        // کار سنگین: ساخت گزارش، تماس با سرویس بیرونی، ...
        Log::info('Report for order '.$this->order->id);
    }

    // بعد از شکست نهایی همه‌ی تلاش‌ها
    public function failed(Throwable $e): void
    {
        Log::error('Report failed: '.$e->getMessage());
    }
}
کدphp
<?php

use App\Jobs\SendOrderReport;

SendOrderReport::dispatch($order);                                  // به صف برو
SendOrderReport::dispatch($order)->delay(now()->addMinutes(10));    // ۱۰ دقیقه بعد
SendOrderReport::dispatch($order)->onQueue('reports');            // صف نام‌دار
SendOrderReport::dispatch($order)->afterCommit();                  // بعد از commit تراکنش دیتابیس
afterCommit

اگر Job را داخل DB::transaction می‌فرستی ولی هنوز commit نشده، Worker ممکن است سفارش را در دیتابیس پیدا نکند. afterCommit() (یا ست‌کردن after_commit در config/queue.php) این مشکل را حل می‌کند.

۳

Worker، شکست و تلاش مجدد

کدbash
php artisan queue:work --tries=3          # اجرای Worker
php artisan queue:work --queue=reports,default   # اولویت صف‌ها
php artisan queue:failed                   # فهرست Jobهای شکست‌خورده
php artisan queue:retry all                # تلاش دوباره برای همه
php artisan queue:retry <id>
php artisan queue:flush                    # پاک‌کردن فهرست شکست‌ها
php artisan queue:restart                  # بعد از هر دیپلوی!
Worker کد را در حافظه نگه می‌دارد

Worker یک‌بار برنامه را بالا می‌آورد و می‌ماند. اگر کد را عوض کنی، Worker تا ریستارت همان کد قدیمی را اجرا می‌کند. بعد از هر تغییر/دیپلوی queue:restart بزن. اگر پروژه‌ات از composer run dev استفاده می‌کند، در حالت توسعه Listener هم راه می‌افتد.

ایمیل در صف، زنجیره و یکتا

کدphp
<?php

use App\Jobs\ChargeWallet;
use App\Jobs\CreateInvoice;
use App\Jobs\SendOrderReport;
use App\Mail\OrderPaid;
use Illuminate\Support\Facades\Bus;
use Illuminate\Support\Facades\Mail;

// ایمیل در صف
Mail::to($user)->queue(new OrderPaid($order));

// زنجیره: به ترتیب؛ اگر یکی شکست خورد بقیه اجرا نمی‌شوند
Bus::chain([
    new CreateInvoice($order),
    new ChargeWallet($order),
    new SendOrderReport($order),
])->dispatch();
کدphp
<?php

namespace App\Jobs;

use Illuminate\Contracts\Queue\ShouldBeUnique;
use Illuminate\Contracts\Queue\ShouldQueue;
use Illuminate\Foundation\Queue\Queueable;

class RebuildSitemap implements ShouldQueue, ShouldBeUnique
{
    use Queueable;

    public function handle(): void { /* ... */ }
}

ShouldBeUnique باعث می‌شود تا وقتی یک نمونه در صف یا در حال اجراست، نمونه‌ی دوم اضافه نشود.

۵

روی سرور واقعی

  • VPS: Worker را با Supervisor اجرا کن تا اگر کرش کرد دوباره بالا بیاید.
  • هاست اشتراکی (cPanel): امکان پروسه‌ی دائمی نیست؛ با Cron هر دقیقه: php artisan queue:work --stop-when-empty.
  • همیشه failed_jobs را مانیتور کن؛ Job شکست‌خورده یعنی ایمیل/پرداختی که انجام نشده.
  • Jobها را «idempotent» بنویس: اگر دوبار اجرا شد، اثرش دوبار نشود (مثلاً قبل از شارژ کیف پول چک کن قبلاً شارژ نشده).
کدtext
[program:laravel-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/app/artisan queue:work --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
numprocs=2
user=www-data
stdout_logfile=/var/www/app/storage/logs/worker.log
stopwaitsecs=3600

تست Job و صف

کدphp
<?php

namespace Tests\Feature;

use App\Jobs\SendOrderReport;
use App\Models\Order;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Illuminate\Support\Facades\Queue;
use Tests\TestCase;

class QueueTest extends TestCase
{
    use RefreshDatabase;

    public function test_job_is_dispatched(): void
    {
        Queue::fake();
        $order = Order::factory()->create();

        SendOrderReport::dispatch($order);

        Queue::assertPushed(SendOrderReport::class, fn ($job) => $job->order->is($order));
    }
}

Job قابل‌اعتماد: تلاش دوباره، Backoff و Timeout

در دنیای واقعی Jobها شکست می‌خورند: API بیرونی قطع است، دیتابیس قفل است، شبکه پریده. یک Job خوب برای شکست طراحی شده است.

کدphp
class SyncInvoiceToAccounting implements ShouldQueue
{
    use Queueable;

    public int $tries = 5;                 // حداکثر تعداد تلاش
    public int $timeout = 60;              // بعد از ۶۰ ثانیه Job کشته شود
    public array $backoff = [30, 120, 600]; // فاصله‌ی تلاش‌ها
    public bool $failOnTimeout = true;

    public function __construct(public Invoice $invoice) {}

    public function handle(AccountingApi $api): void
    {
        $api->push($this->invoice);        // اگر Exception بدهد، دوباره تلاش می‌شود
    }

    public function failed(\Throwable $e): void
    {
        // بعد از آخرین تلاش: به ادمین خبر بده
        Notification::route('mail', 'admin@example.com')->notify(new JobFailed($this->invoice, $e));
    }
}
کدbash
php artisan queue:failed             # فهرست Jobهای شکست‌خورده
php artisan queue:retry 5            # تلاش دوباره‌ی یک Job با شناسه
php artisan queue:retry all          # همه
php artisan queue:forget 5           # حذف یک مورد
php artisan queue:flush              # پاک‌کردن همه‌ی شکست‌ها
Jobهای شکست‌خورده کجا ذخیره می‌شوند؟

در جدول failed_jobs (مایگریشن آن در لاراول از پیش هست). این جدول حافظه‌ی «چه چیزی از دست رفت» است؛ هر هفته نگاهش کن و با queue:prune-failed قدیمی‌ها را پاک کن.

جلوگیری از اجرای تکراری

کدphp
use Illuminate\Contracts\Queue\ShouldBeUnique;
use Illuminate\Queue\Middleware\WithoutOverlapping;
use Illuminate\Queue\Middleware\RateLimited;

class GenerateMonthlyReport implements ShouldQueue, ShouldBeUnique
{
    public function __construct(public int $month) {}
    public function uniqueId(): string { return (string) $this->month; }   // با همین شناسه فقط یکی در صف
    public int $uniqueFor = 3600;

    public function middleware(): array
    {
        return [
            new WithoutOverlapping($this->month),           // دو Job هم‌شناسه هم‌زمان اجرا نشوند
            // new RateLimited('sms'),                      // محدودیت نرخ (مثلاً سقف پیامک در دقیقه)
        ];
    }
}

زنجیره و دسته‌ی Jobها (Chain و Batch)

Chain: Jobها پشت سر هم و فقط اگر قبلی موفق بود. Batch: تعداد زیادی Job موازی با گزارش پیشرفت و یک نتیجه‌ی نهایی.

کدphp
use Illuminate\Support\Facades\Bus;

// زنجیره: اول رندر فاکتور، بعد ایمیل، بعد ثبت در حسابداری
Bus::chain([
    new RenderInvoicePdf($order),
    new EmailInvoice($order),
    new SyncInvoiceToAccounting($order),
])->catch(function (\Throwable $e) {
    logger()->error('invoice chain failed: ' . $e->getMessage());
})->dispatch();
کدbash
php artisan make:queue-batches-table
php artisan migrate
کدphp
// دسته: ارسال خبرنامه برای ۱۰ هزار مشترک
use Illuminate\Bus\Batch;

$jobs = Subscriber::query()->pluck('id')->map(fn ($id) => new SendNewsletterTo($id));

$batch = Bus::batch($jobs)
    ->name('newsletter-2026-10')
    ->allowFailures()                         // شکست چند Job کل دسته را متوقف نکند
    ->then(fn (Batch $b) => logger()->info('همه تمام شد'))
    ->catch(fn (Batch $b, \Throwable $e) => logger()->error('یک Job شکست خورد'))
    ->finally(fn (Batch $b) => logger()->info("{$b->processedJobs()} از {$b->totalJobs} انجام شد"))
    ->onQueue('newsletter')
    ->dispatch();

// بعداً می‌توانی پیشرفت را ببینی
$batch = Bus::findBatch($batchId);
$batch->progress();   // درصد
$batch->cancel();     // لغو

// داخل Job دسته‌ای
public function handle(): void
{
    if ($this->batch()?->cancelled()) return;
    // ...
}
وقتی Batch و Chain را به‌کار ببر

ارسال انبوه ایمیل/پیامک، ساخت گزارش‌های بزرگ، وارد کردن (Import) فایل اکسل با هزاران ردیف؛ همه نمونه‌های واقعی Batch هستند. کاربر منتظر نمی‌ماند و می‌توانی نوار پیشرفت نشان بدهی.

اجرای دائمی Worker: Supervisor، چند صف و Horizon

php artisan queue:work در ترمینال با بستن پنجره می‌میرد. روی سرور باید یک «مدیر پردازه» آن را زنده نگه دارد. در لینوکس معمولاً Supervisor.

کدini
; /etc/supervisor/conf.d/shop-worker.conf
[program:shop-worker]
process_name=%(program_name)s_%(process_num)02d
command=php /var/www/shop/artisan queue:work redis --queue=high,default,low --sleep=3 --tries=3 --max-time=3600
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
user=www-data
numprocs=2
redirect_stderr=true
stdout_logfile=/var/www/shop/storage/logs/worker.log
stopwaitsecs=3600
کدbash
sudo supervisorctl reread
sudo supervisorctl update
sudo supervisorctl start "shop-worker:*"
sudo supervisorctl status
  • --queue=high,default,low: صف‌ها به ترتیب اولویت پردازش می‌شوند؛ ایمیل تأیید را در high و گزارش‌های سنگین را در low بگذار (->onQueue('high')).
  • --max-time=3600: Worker بعد از یک ساعت خودش خارج می‌شود و Supervisor دوباره بالا می‌آورد؛ نشت حافظه جمع نمی‌شود.
  • بعد از هر استقرار: php artisan queue:restart (Worker بعد از اتمام Job فعلی تمیز بسته می‌شود).
  • درایور صف: database برای شروع و پروژه‌های کوچک خوب است؛ برای حجم بالا Redis بهتر است.
  • Horizon داشبورد و مدیریت حرفه‌ای صف روی Redis است (تعداد Workerها، زمان انتظار، شکست‌ها). روی لینوکس/مک کار می‌کند و روی ویندوز به WSL نیاز دارد؛ برای پروژه‌ی جدی ارزشش را دارد.
کدbash
composer require laravel/horizon
php artisan horizon:install
php artisan horizon           # اجرا؛ داشبورد در /horizon (دسترسی را در Gate محدود کن!)
دسترسی داشبورد

Horizon به‌صورت پیش‌فرض فقط در محیط local باز است. در HorizonServiceProvider متد gate() را طوری بنویس که فقط ادمین‌ها بتوانند ببینند؛ داشبوردِ باز یعنی نشت داده.

۱۰

اشتباه‌های رایج

  1. نزدن queue:work و تعجب از اینکه Job اجرا نمی‌شود.
  2. فراموش‌کردن queue:restart بعد از تغییر کد.
  3. فرستادن Job داخل تراکنش بدون afterCommit.
  4. ریختن آبجکت‌های بزرگ یا غیرقابل‌serialize در Job؛ مدل بفرست (فقط شناسه ذخیره می‌شود).
  5. Job غیر idempotent و اجرای دوباره‌ی تلاش‌های ناموفق با اثر تکراری.
  6. نادیده‌گرفتن جدول failed_jobs.
  7. اجرای Worker بدون Supervisor و بی‌خبرماندن از خاموش‌شدنش.
  8. QUEUE_CONNECTION=sync در پروداکشن؛ صف عملاً کار نمی‌کند و ایمیل‌ها پاسخ را کند می‌کنند.
  9. گذاشتن مدل کامل و داده‌ی سنگین داخل Job به‌جای شناسه (حجم صف و کهنه‌شدن داده).
  10. Job غیر Idempotent: اگر دو بار اجرا شود، دو بار مبلغ کسر می‌کند. همیشه فرض کن Job ممکن است تکرار شود.

تمرین‌ها

تمرین ۱
  1. Job به نام GenerateInvoicePdf بساز که در لاگ بنویسد «فاکتور ساخته شد»، و پس از ثبت سفارش آن را dispatch کن.
  2. Worker را اجرا کن و خروجی را در storage/logs/laravel.log ببین.
تمرین ۲
  1. داخل Job عمداً خطا پرت کن، ببین چند بار تلاش می‌شود و بعد در failed_jobs می‌نشیند. خطا را برطرف و queue:retry all بزن.
تمرین ۳
  1. زنجیره‌ای از سه Job بساز و ترتیب اجرا را در لاگ تایید کن؛ سپس وسط زنجیره خطا بده و ببین بقیه اجرا نمی‌شوند.
تمرین ۴
  1. یک Job با tries=4 و backoff بنویس که عمداً دو بار Exception بدهد و بار سوم موفق شود؛ رفتارش را در لاگ ببین. سپس یکی بنویس که همیشه خطا دهد و آن را از queue:failed دوباره اجرا کن.
تمرین ۵
  1. ارسال «ایمیل خوش‌آمد به ۵۰۰ کاربر آزمایشی» را با Batch انجام بده و درصد پیشرفت را با $batch->progress() نمایش بده.
تمرین ۶
  1. Supervisor را روی یک VPS آزمایشی نصب کن، فایل پیکربندی بالا را بگذار و Worker را بکُش؛ ببین خودش بالا می‌آید.
