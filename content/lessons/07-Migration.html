۱

چرا migration؟ خودِ دیتابیس برای چه کم است؟

ساختن جدول در پنلِ دیتابیس (مثل phpMyAdmin یا جدولِ «run SQL») سریع است؛ اما بلای‌اش این است که این کار در هیچ‌جا ثبت نمی‌شود. تصور کن:

  • تیمت دو نفره است؛ تو یک ستون «قیمت» اضافه می‌کنی، نفرِ بعد هم باید همان را با دست اضافه کند.
  • هفته‌ی بعد باید این ستون را برگردانی — کدام کوئری؟ در کدام سرور؟
  • نسخه‌ی جدید توی گیت است ولی شِمای دیتابیس توی هیچ نسخه‌ای ثبت نشده.

Migration یعنی «کنترل‌نسخه برای شمای دیتابیس». هر تغییرِ ساختاری — ساخت جدول، اضافه‌کردنِ ستون، درست‌کردنِ ایندکس — یک فایل PHP می‌شود که مثل بقیه‌ی کدها در گیت می‌رود و با یک دستور اجرا می‌شود. به دستورِ اجرا گفتم: مایگریشن‌ها ردیفِ اجرا را می‌فهمند (تایم‌استمپِ نام فایل) و نظمِ ساختِ جدول‌ها را حفظ می‌کنند.

پس migration چیست؟

یک «جریانِ تکرارشدنی» برای ساختن و تکاملِ ساختارِ دیتابیس: هر فایل مایگریشن یعنی یک قدمِ رو به جلو (up) و یاد می‌دهد که چطور عقب برگردد (down). دیگر هیچ‌کس با دست جدول نمی‌سازد.

۲

ساخت مایگریشن با make:migration

$ php artisan make:migration create_products_table CREATED database/migrations/2026_09_07_000000_create_products_table.php
  • نامِ مایگریشن «انگلیسی و اسمی» می‌خواهد: create_products_table.
  • لاروال از همین نام، اسمِ جدول (products) را حدس می‌زند و قالبِ آماده‌ی Schema::create برایت می‌نویسد.
  • پیشوندِ فایل یک تایم‌استمپ است — ترتیبِ اجرای مایگریشن‌ها با این عدد تعیین می‌شود، نه با تاریخِ گیت.
  • همه‌ی مایگریشن‌ها در database/migrations/ می‌نشینند.

اگر فقط تغییر (نه ساخت اولیه) می‌خواهی، اسمِ متفاوت بده تا قالب فرق کند:

$ php artisan make:migration add_brand_to_products_table $ php artisan make:migration create_reviews_table
فایل قبلی‌ها چه بود؟

در نصبِ تازه‌ی لاراول ۱۳، همین پوشه از قبل جدول‌های پیش‌فرض (users، cache، jobs و…) را دارد. می‌توانی php artisan migrate:status بزنی و نتیجه را بعداً با دستورِ اجرا قیاس کنی.

۳

Schema::create و متدهای up / down

هر فایل مایگریشن دو متد دارد. فایلcreate_products_table.php را باز کن:

کدdatabase/migrations/..._create_products_table.php
<?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Database\Schema\Blueprint;
use Illuminate\Support\Facades\Schema;

return new class extends Migration
{
    public function up(): void
    {
        Schema::create('products', function (Blueprint $table) {
            $table->id();
            $table->string('name');
            $table->text('description');
            $table->unsignedBigInteger('price');
            $table->timestamps();
        });
    }

    public function down(): void
    {
        Schema::dropIfExists('products');
    }
};
  • up() = قدمِ روبه‌جلو: جدولِ products را با ستون‌هایش می‌سازد.
  • down() = برعکس: همان جدول را حذف می‌کند، تا اگر لازم شد، «عقب‌گرد» ممکن باشد.
  • داخلِ کلاسِ بی‌نامِ کلوسورِ Schema::create، پارامترِ $table از نوع Blueprint است و «ستون‌سازی» را انجام می‌دهد.
  • $table->timestamps() به‌طور خودکار دو ستونِ created_at و updated_at می‌سازد — قراردادی که Eloquent بعداً از آن لذت می‌برد.
قانونِ طلایی

بعد از اینکه یک مایگریشن در تیم/سرور اجرا شد، آن را ویرایش نکن؛ اگر چیزی را اشتباه ساخته‌ای، یک مایگریشنِ جدید «اصلاحی» بنویس. چون ویرایشِ قدیمی یعنی مغایرت با ماشینِ بقیه. (در مرحله‌ی یادگیری که فعلی است، از migrate:rollback استفاده کن.)

۴

تیپ‌های رایج ستون

Blueprint برای هر تیپ یک متد دارد. مهم‌ترین‌ها برای این دوره:

متدستونِ ساخته‌شدهکاربردِ ما
$table->id()کلید اصلیِ خودافزایششناسه‌ی هر رکورد (همیشه)
$table->string('name')VARCHARنام، عنوان، ایمیل، اسلاگ — متنِ کوتاه
$table->text('desc')TEXTتوضیحاتِ بلندِ محصول
$table->integer('count')INTEGERموجودی و شمارنده‌ها
$table->unsignedBigInteger('price')UNSIGNED BIGINTقیمت (بدون منفی و بزرگ)
$table->boolean('is_active')BOOLEANعلامت‌گذاریِ فعال/غیرفعال
$table->foreignId('category_id')UNSIGNED BIGINTکلید خارجی (درس بعد)
$table->timestamps()created_at / updated_atزمانِ ثبت و ویرایش

و «اصلاح‌کننده‌های» پرتکرار روی هرکدام:

کدداخل Schema::create
$table->string('email')->unique();
$table->text('bio')->nullable();
$table->integer('stock')->default(0);
$table->foreignId('user_id')->nullable();
  • ->nullable() یعنی ستون خالی پذیرفته است؛ ->default(0) مقدارِ پیش‌فرض.
  • ->unique() یک ایندکسِ یکتا می‌سازد (مثلاً برای ایمیل).
۵

کلید خارجی: foreignId و constrained

محصول ما به یک دسته‌بندی وابسته است. پس اول جدولِ categories را می‌سازیم، بعد داخل products یک ستونِ category_id که «اشاره» به آن داشته باشد:

کد..._create_products_table.php
Schema::create('products', function (Blueprint $table) {
    $table->id();
    $table->string('name');
    $table->text('description');
    $table->unsignedBigInteger('price');
    $table->foreignId('category_id')
        ->constrained()
        ->cascadeOnDelete();
    $table->timestamps();
});
  • $table->foreignId('category_id') ستونی از جنس کلید (UNSIGNED BIGINT) می‌سازد.
  • ->constrained() با حدس‌زدن (پاک کردن پسوندِ _id از نام ستون) به جدولِ categories وصلش می‌کند و یک محدودیتِ کلید خارجی تعریف می‌کند: مقدارِ این ستون باید در جدولِ مرجع وجود داشته باشد.
  • ->cascadeOnDelete(): اگر دسته‌بندی حذف شود، محصولاتِ خودش هم پاک می‌شوند (رفتارِ پیش‌فرضِ «جلوگیری کن» یعنی restrict بود؛ اینجا صریحاً cascade می‌گوییم).
چه می‌شود در SQL؟

در MySQL این یعنی محدودیتِ FOREIGN KEY (category_id) REFERENCES categories (id) ON DELETE CASCADE. در SQLite هم معادلِ خودش. فکر نکن قرار است کوئری بنویسیم — این‌ها را migration می‌سازد.

گزینه‌های حذف

->restrictOnDelete() (حذفِ والد را ممنوع کن)، ->nullOnDelete() (به‌جای حذفِ فرزند، این کلید را null کن). برای دسته‌بندی، cascade منطقی است.

۶

تغییر جدولِ موجود با Schema::table

جدول products ساخته شده و اجرا رفته؛ حالا یک ستون اضافه می‌کنیم. با Schema::table (نه create) فایلِ اصلاحی می‌سازیم:

$ php artisan make:migration add_is_active_to_products_table
کد..._add_is_active_to_products_table.php
return new class extends Migration
{
    public function up(): void
    {
        Schema::table('products', function (Blueprint $table) {
            $table->boolean('is_active')->default(true);
        });
    }

    public function down(): void
    {
        Schema::table('products', function (Blueprint $table) {
            $table->dropColumn('is_active');
        });
    }
};
  • Schema::table('products', ...) جدولِ موجود را «باز» می‌کند تا چیزی اضافه یا کم کنی؛ جدول را از نو نمی‌سازد.
  • در down() با ->dropColumn('is_active') همان اضافه‌شده را برمی‌گردانی — یعنی هر up یک down دارد.
  • برای برداشتنِ کلِ جدول هم Schema::dropIfExists('products') در downِ مایگریشنِ اولیه نوشته شده بود.
down باید دقیقِ برعکسِ up باشد

اگر down کاری نکند یا اشتباه باشد، رول‌بکِ بعدی یا از کار می‌افتد یا ساختار را خراب می‌کند. برای افزودنِ ستون، در down حذف‌اش کن؛ برای ساختِ جدول، در down حذفِ جدول — این قانون است.

۷

اجرا، وضعیت و بازگشت

حالا فرمان‌های اصلی که تا آخر این دوره بارها می‌زنی:

$ php artisan migrate
$ php artisan migrate:status Ran? Migration Batch 0001_01_01_000000_create_users_table 1 0001_01_01_000001_create_cache_table 1 2026_09_07_000000_create_products_table
خروجی نمونهتوضیحِ ستون‌ها

= اجرا شده؛ = در انتظار. ستونِ «Batch» شماره‌ی دسته‌ی اجراست.

بعد از migrate، مایگریشنِ ما هم می‌شود.

$ php artisan migrate:rollback # برگرداندنِ آخرین دسته (batch) — اجرای downها $ php artisan migrate:rollback --step=1 # فقط یکی $ php artisan migrate:fresh # حذف همه + اجرای مجدد (فقط dev!) $ php artisan migrate --force # بدون prompt، برای production
  • migrate فقط مایگریشن‌های «اجرانشده» را اجرا می‌کند؛ سالم است و تکراری صدمه نمی‌زند.
  • migrate:rollback برعکسِ آخرین دسته‌ی کامل (downِ همه‌ی آن‌ها)، نه فقط آخرین فایل.
  • migrate:fresh همه‌ی جدول‌ها را می‌اندازد و دوباره می‌سازد — در توسعه مفید، در production مرگبار. آنجا فقط migrate (و --force) را صدا بزن.
دیتابیس پیش‌فرض

نصبِ تازه‌ی لاراول با SQLite می‌آید و بدون هیچ تنظیمی همین کار می‌کند (فایلِ database/database.sqlite). اگر MySQL داری، در .env مقدارهای DB_CONNECTION=mysql و... را بگذار؛ بقیه‌ی این درس‌ها فرقی نمی‌کند.

۸

گام پروژه: جدول‌های فروشگاه

شِمای واقعیِ فروشگاه کوچک

دو جدولِ اصلیِ فروشگاه را الان می‌سازیم؛ در درسِ بعدی (Eloquent) با همین‌ها مدل می‌سازیم.

  1. php artisan make:migration create_categories_table — داخل up(): id، string('name') و string('slug')->unique()، به‌علاوه timestamps(). در down(): dropIfExists.
  2. php artisan make:migration create_products_table — جدولِ محصول با: string('name')، text('description')، unsignedBigInteger('price')، boolean('is_active')->default(true) و کلید خارجیِ foreignId('category_id')->constrained()->cascadeOnDelete().
  3. php artisan migrate — اجرا کن و بعد php artisan migrate:status — هر دو قرمزِ باید سبزِ شوند.
  4. اگر چیزی را خطا دیدی: php artisan migrate:rollback، فایل را اصلاح کن و دوباره migrate.
بعدش چه؟

در درس ۰۸ یک Product و Category به‌عنوان «مدل» می‌سازیم که همین جدول‌ها را بخوانند و بنویسند — بدونِ حتی یک خط SQLِ دستی. رابطه‌ی category/فرزندِ محصول جایی است که constrained امروز نفس می‌کشد.

۹

تمرین‌ها؛ حالا نوبت توست!

تمرین ۱: ستونِ «برند»
  1. مایگریشنِ add_brand_to_products_table بساز.
  2. در up() ستونِ string('brand') و در down() dropColumn('brand') بنویس.
  3. اجرا کن، با migrate:status چک کن، بعد rollback بزن و دوباره جلو برو.
تمرین ۲: جدولِ دیدگاه‌ها
  1. مایگریشنِ create_reviews_table بساز.
  2. ستون‌ها: id، text، tinyInteger('rating')->default(5) و foreignId('product_id')->constrained()->cascadeOnDelete() با timestamps().
  3. اجرا کن و migrate:status را ببین؛ جدولِ جدید در کنار بقیه ظهور کرده است.
چالش

یک ایندکس به ستونِ rating در جدولِ reviews اضافه کن (راهنما: $table->index('rating') و در down() با dropIndex برش کن). بعد از آن، ایندکس را در migrate:status پیگیری کن.

چیزی که از این بخش توی ذهنت بماند

  1. migration = کنترل‌نسخه‌ی ساختارِ دیتابیس؛ هر فایل یعنی up (جلو) و down (عقب).
  2. ساخت: make:migration create_xxx_table؛ تغییر: make:migration add_yyy_to_xxx_table.
  3. Schema::create برای جدولِ نو، Schema::table برای جدولِ موجود.
  4. تیپ‌های پرکاربرد: id(), string(), text(), integer(), boolean(), timestamps().
  5. رابطه: foreignId('x_id')->constrained()->cascadeOnDelete().
  6. اجرا: migrate؛ وضعیت: migrate:status؛ عقب: migrate:rollback؛ بازسازی: migrate:fresh (فقط dev).
  7. بعد از اجرا، مایگریشنِ اجراشده را ویرایش نکن — فایل «اصلاحی» بنویس.
