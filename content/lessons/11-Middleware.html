Middleware

می‌خواهیم بعضی روت‌ها فقط برای بعضی کاربران باز باشد. Middleware یعنی «درِ ورودیِ مطمئن» برای روت‌ها — دقیقاً همان‌چیزی که در درس‌های قبل بدون معرفی، هر روز برای‌مان کار می‌کرد.

۱

Middleware چیست؟

Middleware یعنی «یک لایه» که هر درخواستِ HTTP باید از آن رد شود تا به کنترلر برسد. مثل درِ ساختمانی که «کارت می‌خواهیم»، «بلیت می‌خواهیم» یا «به این فرد اجازه نمی‌دهیم» را چک می‌کند:

دریافتِ درخواست مرورگر می‌خواهد /admin را ببیند
Middleware (دَروازه) چکِ ورود، چکِ نقش، چکِ CSRF، …
کنترلر + پاسخ فقط بعدِ عبورِ همه‌ی دروازه‌ها

اگر دروازه عبور کرد، درخواست «همان‌طور» به لایه‌ی بعدی یا کنترلر می‌رسد؛ اگر نه، middleware چیزی برمی‌گرداند — معمولاً redirect یا پاسخِ خطا مثل abort(403). این یعنی middleware می‌تواند «جلوتر» از کنترلر، درخواست را قطع کند.

جالب است که درِ خروج هم middleware دارد: می‌توانی قبل از تحویلِ پاسخ به مرورگر، چیزی به آن اضافه کنی — مثلاً یک هدر. پس middleware هم «قبل» و هم «بعد» از کنترلر می‌تواند کار کند.

از کجا آشناست؟

از درسِ ۴ که PreventRequestForgery (همان توکنِ @csrf درسِ ۱۰) در همه‌ی روت‌های POST بود، دقیقاً همان middleware است. یعنی تو از قبل با «کاربرد»ش آشنا بوده‌ای؛ الان ساختارش را یاد می‌گیری.

۲

ترتیبِ اجرا

middleware مثل پیاز است: درخواست لایه‌ها را «از بیرون به داخل» می‌پیماید تا به هسته (کنترلر) برسد و پاسخ «از داخل به بیرون» برمی‌گردد. بنابراین ترتیبِ ثبتِ middleware مهم است:

کدschematic — لایه‌ها
Request ──► [A] ──► [B] ──► [C] ──► Controller ──► Response ◄── [C] ◄── [B] ◄── [A] ◄── Response
            ورود         ورود

کدِ بعد از $next($request)، «بعد از کنترلر» اجرا می‌شود. برای خیلی از کارها مهم است که کدام را می‌خواهی:

کدPHP — قبل و بعد از کنترلر
public function handle(Request $request, Closure $next): Response
{
    // اینجا قبل از کنترلر اجرا می‌شود  (مثلاً چکِ دسترسی)

    $response = $next($request);

    // اینجا بعد از کنترلر اجرا می‌شود   (مثلاً افزودن هدر به پاسخ)

    return $response;
}
دو راهِ «قطع کردن»

داخلِ middleware می‌توانی یا redirect()->to(...) برگردانی، یا abort(403) بدهی (یا abort(404) برای «اظهارِ عدمِ وجود»). هر دو یعنی «عبور نکن». اگر هیچ‌یک نبود، با $next($request) درخواست را راه بده.

۳

ساخت با make:middleware

ساختِ middleware مثل بیشترِ چیزها در Laravel — با artisan:

$ php artisan make:middleware EnsureTokenIsValid INFO Middleware [app/Http/Middleware/EnsureTokenIsValid.php] created successfully.
  • نامِ کلاس را به‌صورتِ CamelCase بگو (مثل مدل‌ها).
  • فایل در app/Http/Middleware می‌شود — پیش‌فرضِ laravel برای middlewareهای خودت.
  • متدِ اصلی همان handle است که این‌بار درش را خودمان پر می‌کنیم.
۴

نوشتنِ بدنه‌ی middleware

متدِ handle سه چیز می‌گیرد: $request (درخواستِ فعلی)، یک Closure به اسمِ $next («بده به بعدی»)، و ممکن است پارامترهایِ اضافه. الگویِ پایه:

کدapp/Http/Middleware/EnsureTokenIsValid.php
<?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class EnsureTokenIsValid
{
    /**
     * @param  \Closure(\Illuminate\Http\Request): (\Symfony\Component\HttpFoundation\Response)  $next
     */
    public function handle(Request $request, Closure $next): Response
    {
        if ($request->input('token') !== 'my-secret-token') {
            return redirect('/home');
        }

        return $next($request);
    }
}
  • مثالی کاملاً ساختگی از داکِ رسمی: فقط کسی می‌شود بگذرد که مقدارِ token را در ورودی داشته باشد — وگرنه به /home کشانده می‌شود.
  • $request->input('token') برایِ GET و POST هر دو کار می‌کند.
  • $next($request) یعنی «درخواست را به لایه‌ی بعدی / کنترلر بده و جوابش را بردار».
  • نوعِ بازگشت Response؛ پس returnِ آخر پاسخِ واقعیِ برنامه است.
چه چیزهایی می‌شود این‌جا داشت؟

چون middlewareها از container ساخته می‌شوند، در constructor می‌توان هر سرویسی را به آن تزریق کرد (مثل Logger). خیلی از لایه‌هایِ قدرتمند (rate-limit، تاییدِ ایمیل، CSRF و …) دقیقاً با همین مکانیزمِ ساده ساخته شده‌اند.

۵

ثبتِ سراسری (Global)

ساختِ middleware کافی نیست؛ باید «ثبت»ش کنی تا واردِ سیستم شود. دو جور ثبت داریم. اولی سراسری — یعنی برایِ همه‌ی روت‌ها اجرا می‌شود. در bootstrap/app.php:

کدbootstrap/app.php — داخلِ withMiddleware
use App\Http\Middleware\EnsureTokenIsValid;
use Illuminate\Foundation\Configuration\Middleware;
use Illuminate\Foundation\Application;

// ...

->withMiddleware(function (Middleware $middleware): void {
    $middleware->append(EnsureTokenIsValid::class);   // اضافه کن به آخرِ فهرستِ سراسری
})
  • ->append(...) یعنی به انتهایِ فهرستِ سراسری؛ ->prepend(...) یعنی به سرِ آن.
  • فایل bootstrap/app.php همان جایی است که سرنوشتِ پروژه را با ->withRouting(...) و ->withMiddleware(...) و ->withExceptions(...) می‌نویسی.
  • چند middleware؟ آرایه بده: $middleware->append([First::class, Second::class]).
سراسری یعنی همه‌جا

چیزهایی مثلِ TrimStrings و StartSession در فهرستِ سراسری می‌نشینند. برایِ «نقشِ کاربرِ خاص رویِ روتِ خاص»، middleware سراسری مناسب نیست — ثبت رویِ روت را ببین.

۶

ثبت رویِ روت

دومین روش: middleware را مستقماً به یک روت (یا گروهِ روت) وصل کن:

کدroutes/web.php
use App\Http\Middleware\EnsureTokenIsValid;

Route::get('/profile', function () {
    // ...
})->middleware(EnsureTokenIsValid::class);

// چندتایی:
Route::get('/admin', function () {
    // ...
})->middleware([First::class, Second::class]);

// رویِ گروهِ روت:
Route::middleware([EnsureTokenIsValid::class])->group(function () {
    Route::get('/a', function () { /* ... */ });
    Route::get('/b', function () { /* ... */ });
});
  • با ->middleware(ClassName::class) همان کلاس را وصل کن.
  • با Route::middleware([...])->group(...) یک‌جا رویِ چند روت بگذار — در این بخشِ پروژه استفاده می‌شود.
  • اگر یک روتِ داخلِ گروه باید معاف باشد: Route::get('/b', ...)->middleware([...])->withoutMiddleware(EnsureTokenIsValid::class).
alias چیست و کجاست؟

به‌جای نوشتنِ نامِ کاملِ کلاس در هر روت، می‌توانی یک اسمِ کوتاه (alias) برایش تعریف کنی — مثلاً 'admin'. نتیجه‌اش می‌شود: ->middleware('admin'). درسِ بعد سراغِ همین می‌رود.

۷

alias و گروه‌های web/api

۱) alias. یک نامِ کوتاه برایِ کلاسِ middleware، در bootstrap/app.php:

کدbootstrap/app.php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'check-role' => CheckRole::class,
        'is-admin'   => EnsureUserIsAdmin::class,
    ]);
})

حالا درِ روت کوتاه و خوانا: ->middleware('check-role:admin'). چند aliasِ آماده‌ی Laravel که حتماً می‌بینی: auth (رمزِ ورود لازم است)، guest (برعکس — مهمان‌ها فقط)، verified، throttle، can، password.confirm.

۲) گروه‌های web و api. Laravel دو گروهِ آماده دارد که پرونده به‌صورتِ خودکار رویِ فایلِهایِ روتِشان می‌شود:

گروهروت‌هامهم‌ترین‌ها درونِ آن
webroutes/web.phpStartSession، ShareErrorsFromSession، PreventRequestForgery (همان @csrf!)، SubstituteBindings
apiroutes/api.phpSubstituteBindings (بدونِ session؛ بدونِ CSRF)
  • پس کلاسِ ما در routes/web.php بدونِ هیچ‌کاری session، $errors و CSRF را دارد؛ درِ api ندارد.
  • اگر می‌خواهی middleware خودت را به گروهِ web اضافه کنی: $middleware->web(append: [CheckRole::class]).
  • برای افزودن به پشته‌ی سراسری: $middleware->append(...)؛ برای حذف از گروهِ web: $middleware->removeFromGroup('web', CheckRole::class).
پس چرا فرمِ درسِ ۱۰ بدونِ کارِ اضافه جواب داد؟

چون روت‌های استور در گروهِ web بودند و درِ گروهِ web شاملِ PreventRequestForgery («همانِ @csrf») و ShareErrorsFromSession («همانِ $errors») است. همه‌چیز گره خورده است!

۸

middleware با پارامتر

گاهی middleware باید مقدار بگیرد — مثل «نقشِ مربوطه». پارامتر بعد ازِ $next می‌آید، و درِ روت با نام:مقدار داده می‌شود:

کدEnsureUserHasRole.php
public function handle(Request $request, Closure $next, string $role): Response
{
    if (! $request->user() || $request->user()->role !== $role) {
        abort(403, 'شما به این صفحه دسترسی ندارید');
    }

    return $next($request);
}
کدroutes/web.php
// با alias:
Route::get('/admin', [DashboardController::class, 'index'])
    ->middleware('check-role:admin');

// مستقیم با کلاس:
Route::put('/post/{id}', function (string $id) { /* ... */ })
    ->middleware(EnsureUserHasRole::class.':editor');

// چند پارامتر با کاما:
Route::put('/post/{id}', ...)->middleware(EnsureUserHasRole::class.':editor,publisher');
  • دقت کن: با کلاس، رشته را با . و دونقطه می‌سازی؛ با alias فقط 'check-role:admin'.
  • $request->user() درِ کاربرِ لاگین‌کرده را می‌دهد — بعدِ درسِ ۱۲ که احرازِ هویت را می‌نصب کنیم، دیگر خالی نیست.
پارامتر و «مقدارِ» روت را اشتباه نگیر

check-role:admin پارامترِ middleware است، نه پارامترِ URL. پارامترِ URL همان {id} است (که در روتِ پوت بالا می‌بینی). این‌ها را با هم جای‌به‌جایی نکن.

۹

گام پروژه: CheckRole

تکمیلی: صفحه‌ی مدیر فروشگاه را «قفل» می‌کنیم

پنلِ مدیریت را روی /admin می‌گذاریم و با یک middleware فقط به کاربرانی می‌دهیم که نقش‌شان admin است — بقیه خطای ۴۰۳ می‌گیرند.

  1. ساختِ middleware و alias:
$ php artisan make:middleware CheckRole
کدبعد: app/Http/Middleware/CheckRole.php
<?php

namespace App\Http\Middleware;

use Closure;
use Illuminate\Http\Request;
use Symfony\Component\HttpFoundation\Response;

class CheckRole
{
    public function handle(Request $request, Closure $next, string $role): Response
    {
        if (! $request->user() || $request->user()->role !== $role) {
            abort(403);
        }

        return $next($request);
    }
}
  1. ثبتِ alias در bootstrap/app.php:
کدbootstrap/app.php
->withMiddleware(function (Middleware $middleware): void {
    $middleware->alias([
        'check-role' => CheckRole::class,
    ]);
})
  1. گروهِ روتِ /admin با همان دروازه:
کدroutes/web.php
Route::middleware('check-role:admin')->group(function () {
    Route::get('/admin', [DashboardController::class, 'index'])->name('admin.dashboard');
    // ... و هر روتِ مدیریتیِ دیگر
});
بعدی

فعلاً $request->user() همیشه خالی است و همه خطای ۴۰۳ می‌گیرند، چون هنوز «ورودِ کاربر» نداریم. در درسِ ۱۲ با auth کاربر را وارد می‌کنیم و بعد از آن، این پنل واقعاً قفل می‌شود. تا آن موقع همین middleware را نگه دار.

۱۰

تمرین‌ها؛ حالا نوبت توست!

تمرین ۱: دروازه‌ی محلی
  1. با php artisan make:middleware EnsureLocalRequest یک middleware بساز که فقط وقتی $request->ip() === '127.0.0.1' یا '::1' باشد ادامه دهد، وگرنه abort(403).
  2. به روتِ /admin وصلش کن (حتی قبلِ اتصالِ CheckRole).
  3. با php artisan route:list ببین ستونِ Middleware چه می‌گوید.
تمرین ۲: لاگِ درخواست
  1. middleware بساز که Request::url() و Request::method() را با Log::info(...) در storage/logs/laravel.log بنویسد — «قبلِ» کنترلر.
  2. این‌بار هم‌پیمانِ «بعدِ» $next بنویس که بنویسد «پاسخِ آماده است»؛ اجراش کن و ترتیبِ دو خطِ لاگ را در فایل ببین.
چالش

تمرینِ ۲ را «terminable» کن: متدِ terminate(Request, Response) اضافه کن که بعد ازِ ارسالِ پاسخ به مرورگر، لاگی دیگر بنویسد (زمانِ صرف‌شده). ببین فرقش با بعدِ $next در چیست — hint: $next هنوز ارسالِ پاسخ را ندارد؛ terminate بعدِ ارسال است.

چیزی که از این بخش توی ذهنت بماند

  1. Middleware = لایه‌ای «قبل و بعد» از کنترلر؛ handle(Request, Closure $next) و $next($request).
  2. با php artisan make:middleware Name می‌سازی؛ داخلِ app/Http/Middleware می‌نشیند.
  3. دو نوعِ ثبت: سراسری ($middleware->append/prepend) و رویِ روت (->middleware(...)).
  4. aliasها نامِ کوتاهِ middlewareها هستند ('auth'، 'check-role'، …) و به‌جایِ کلاس درِ روت می‌آمدند.
  5. گروهِ web خودِ CSRF و $errors را دارد؛ گروهِ api نه.
  6. پارامتر: middleware('نام:مقدار') — فقط «رشته‌یِ کلاس» را با . می‌چسبانی.
