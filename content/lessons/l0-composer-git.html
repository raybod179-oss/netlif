Composer چیست؟

Composer «مدیر بسته‌های PHP» است؛ مثل npm در دنیای جاوااسکریپت. به‌جای اینکه کتابخانه‌ها را دستی دانلود و کپی کنی، یک دستور می‌زنی و Composer آن‌ها (و وابستگی‌هایشان) را نصب می‌کند. خود لاراول هم با Composer نصب می‌شود.

کدbash
composer --version
# اگر نصب نیست: از getcomposer.org نصب‌کننده‌ی ویندوز را اجرا کن و ترمینال را از نو باز کن

composer create-project laravel/laravel my-app   # ساخت پروژه‌ی لاراول
cd my-app
۲

composer.json، composer.lock و vendor

فایل/پوشهنقشدر گیت؟
composer.jsonفهرست بسته‌های موردنیاز و تنظیمات (دستی/با دستور)بله
composer.lockنسخه‌ی دقیقِ نصب‌شده؛ برای اینکه همه‌ی تیم نسخه‌ی یکسان داشته باشندبله
vendor/خود کدِ بسته‌ها؛ با composer install دوباره ساخته می‌شودنه (در .gitignore)
کدbash
composer require nesbot/carbon          # نصب یک بسته
composer require phpunit/phpunit --dev   # فقط برای توسعه
composer remove nesbot/carbon          # حذف
composer install                       # نصب همه از روی lock (بعد از clone)
composer update                        # به‌روزرسانی طبق محدوده‌ی نسخه
install یا update؟

روی پروژه‌ی موجود (بعد از clone) install بزن. update نسخه‌ها را عوض می‌کند و ممکن است چیزی را خراب کند؛ آگاهانه و روی شاخه‌ی جدا انجامش بده.

Autoload و PSR-4

Composer یک فایل vendor/autoload.php می‌سازد. با یک require همه‌ی کلاس‌ها بدون require دستی لود می‌شوند. قاعده‌ی PSR-4 می‌گوید «نام namespace = مسیر پوشه».

کدjson
{
    "autoload": {
        "psr-4": { "App\\": "app/" }
    }
}
کدphp
<?php
// app/Services/Greeter.php
namespace App\Services;

class Greeter
{
    public function hello(string $name): string
    {
        return "سلام $name";
    }
}

// index.php
require __DIR__ . "/vendor/autoload.php";

use App\Services\Greeter;

echo (new Greeter())->hello("Rayvo");

بعد از اضافه‌کردن یک پوشه‌ی جدید به autoload یک‌بار composer dump-autoload بزن. این همان سازوکاری است که App\Models\User را در لاراول پیدا می‌کند.

Git: دوربین زمان برای کدهایت

Git تاریخچه‌ی تغییرات پروژه را نگه می‌دارد. هر commit یک عکس از کل پروژه است که هر وقت بخواهی به آن برمی‌گردی. بدون Git یک اشتباه ساده می‌تواند ساعت‌ها کارت را بسوزاند.

کدbash
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"

git init                      # شروع ردگیری پروژه
git status                    # چه چیزی عوض شده؟
git add .                     # همه‌ی تغییرات را برای commit آماده کن
git commit -m "feat: add product list page"
git log --oneline             # تاریخچه‌ی کوتاه
git diff                      # دیدن دقیق تغییرات هنوز add‌نشده
۵

.gitignore و خطر .env

کدtext
/vendor
/node_modules
.env
/storage/*.key
.DS_Store
فایل .env هرگز commit نشود

داخل .env رمز دیتابیس، کلید برنامه و توکن‌های درگاه است. اگر آن را روی GitHub بگذاری، حتی بعد از حذف، در تاریخچه می‌ماند. اگر اشتباهاً رفت: همان رمزها را فوراً عوض کن (فقط حذف فایل کافی نیست). لاراول از قبل .env را در .gitignore دارد؛ دستکاری‌اش نکن.

۶

شاخه (Branch) و ادغام

کدbash
git switch -c feature/cart        # ساخت و رفتن به شاخه‌ی جدید
# ... کار کن و commit بزن ...
git switch main
git merge feature/cart         # ادغام
git branch -d feature/cart     # حذف شاخه‌ی تمام‌شده

عادت خوب: هر قابلیت یک شاخه. شاخه‌ی main همیشه باید سالم و قابل‌اجرا باشد.

۷

GitHub: ذخیره‌ی ابری و پورتفولیو

کدbash
# 1) در github.com یک Repository خالی بساز (ترجیحاً Private برای پروژه‌ی خصوصی)
git remote add origin https://github.com/USERNAME/my-app.git
git branch -M main
git push -u origin main

# برداشتن پروژه‌ی دیگران یا خودت روی کامپیوتر جدید
git clone https://github.com/USERNAME/my-app.git
cd my-app
composer install
cp .env.example .env && php artisan key:generate
پیام commit خوب

کوتاه و دقیق بنویس: fix: calculate cart total with discount بهتر از «اصلاح». پیشوندهای رایج: feat، fix، docs، refactor، test. در درس پورتفولیو می‌بینی چرا GitHub مرتب، رزومه‌ی تو است.

۸

اشتباه‌های رایج

  1. commit کردن vendor و .env.
  2. زدن git add . بدون نگاه به git status.
  3. کار مستقیم روی main برای تغییر بزرگ.
  4. ترس از Git و commit نزدن تا آخر روز؛ commit کوچک و مکرر بزن.
  5. اجرای composer update روی پروژه‌ی در حال کار بدون اینکه lock را بررسی کنی.
  6. تداخل (conflict) را بدون خواندن علامت‌های <<<<<<< حل‌کردن؛ فایل را باز کن، هر دو نسخه را بخوان و یکی (یا ترکیب) را نگه دار.
★

تمرین‌ها

تمرین ۱: Composer
  1. پروژه‌ای خالی با composer init بساز و بسته‌ی nesbot/carbon را نصب کن؛ تاریخ فردا را چاپ کن.
  2. اتولود PSR-4 را برای پوشه‌ی src تنظیم و یک کلاس تستی لود کن.
تمرین ۲: Git
  1. یک پوشه‌ی تازه بساز، git init کن، ۳ commit بزن و با git log --oneline ببین.
  2. یک شاخه بساز، فایلی عوض کن، به main برگرد و merge کن. یک‌بار هم عمداً conflict بساز و حلش کن.
تمرین ۳: GitHub
  1. یک Repo بساز و پروژه را push کن. مطمئن شو .env و vendor بالا نرفته‌اند.
