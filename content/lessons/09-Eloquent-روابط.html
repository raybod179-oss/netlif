۱

چرا رابطه لازم است؟

در درس ۰۷، جدولِ products یک ستونِ category_id داشت که با foreignId("...")->constrained() به جدولِ categories وصل شد. یعنی در سطحِ دیتابیس رابطه هست. اما در سطحِ کد، تا هنوز نمی‌دانیم «محصولِ من چه دسته‌بندی دارد». Eloquent با متدِ رابطه این را روشن می‌کند:

بدونِ رابطه:

  • گرفتنِ محصول → خواندنِ category_id → یک پرس‌وجویِ جدا برای دسته‌بندی.
  • هر صفحه‌ای که به محصول و دسته‌اش نیاز دارد، باید این را دوباره بنویسد — و معمولاً غلط.

با رابطه: $product->category و $category->products — همین. Eloquent کوئری درست را می‌سازد.

انواعِ رابطه‌ای که این بخش می‌آموزیم:

نوعمعنیمثالِ این پروژه
hasManyیک، چند تا می‌زایددسته‌بندی ↔ محصول‌ها
belongsToچندتا، به یکی تعلق دارندمحصول → دسته‌بندی
hasOneیک، دقیقاً یک تا داردکاربر ↔ پروفایل
belongsToManyچند، با چند (واسط)شاید: محصول ↔ برچسب‌ها
۲

دسته ↔ محصول: hasMany و belongsTo

روی محصول (سمتِ «یکی» از طرفِ چندتاست) رابطه‌ی belongsTo را بگذار:

کدapp/Models/Product.php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\BelongsTo;

#[Fillable('name', 'description', 'price', 'category_id')]
class Product extends Model
{
    public function category(): BelongsTo
    {
        return $this->belongsTo(Category::class);
    }
}

و روی دسته‌بندی (سمتِ یک‌تاژ) رابطه‌ی hasMany را:

کدapp/Models/Category.php
<?php

namespace App\Models;

use Illuminate\Database\Eloquent\Model;
use Illuminate\Database\Eloquent\Relations\HasMany;

class Category extends Model
{
    public function products(): HasMany
    {
        return $this->hasMany(Product::class);
    }
}
  • belongsTo در کلیدی که محصول دارد (category_id) می‌گردد؛ hasMany یعنی «همه‌ی رکوردهایِ محصولی که category_idشان من است».
  • نامِ متد را زنده کن؛ $product->category() یک «کوئری‌بیلدرِ رابطه» برمی‌گرداند که قابلِ ادامه‌دادن است، ولی $product->category اجرا و نتیجه را تحویل می‌دهد.

استفاده‌اش:

کدPHP
$category = Category::find(1);

$products = $category->products;        // Collection از همه‌ی محصول‌هایِ این دسته
$cheap    = $category->products()      // رابطه‌ی قابلِ ادامه
    ->where('price', '<', 200000)
    ->get();

$product = Product::find(1);
$name    = $product->category->name;   // نامِ دسته‌یِ این محصول — یک مدل
کلیدهایِ پیش‌فرض

Eloquent بدونِ پرسیدن حدس می‌زند: در hasMany(Product::class) دنبالِ ستونِ category_id در جدولِ products است. چون متدمان products() نام دارد، ستونِ موردنظر از رویِ نامِ کلاسِ مادر (Category) ساخته می‌شود، نه نامِ متد — پس هرچی نامِ متد بده، درست کار می‌کند.

۳

یک‌به‌یک: hasOne

وقتی هر رکوردِ یک جدول، دقیقاً یک رکوردِ جدولِ دیگر را دارد. مثالِ کلاسیک این‌جا نیست ولی برای پروفایلِ کاربر یا «گذرنامه» عادی است. مثلِ hasMany، ولی نتیجه‌اش یک مدل است، نه Collection:

کدapp/Models/User.php
use Illuminate\Database\Eloquent\Relations\HasOne;

public function profile(): HasOne
{
    return $this->hasOne(Profile::class);
}

// $user->profile->avatar — بدون هیچ کار اضافه
رابطه = دوطرفه

hasOne/hasMany «از والد به سمتِ فرزند» است؛ همیشه یک belongsTo مقابلش (رویِ جدولِ دارایِ کلیدِ خارجی) تعریف بکن تا از آن سمت هم دسترسی‌پذیر باشد.

۴

چند‌به‌چند: belongsToMany و جدولِ واسط

محصول می‌تواند چند «برچسب» داشته باشد و یک برچسب هم به چند محصول بخورد — نه category_id جا دارد و نه طرفِ مقابل. راه‌حل، یک جدولِ واسط است:

products product_tag tags id ← PK product_id FK id ← PK name tag_id FK name price slug

فقط دو مدل لازم است؛ جدولِ واسط را مایگریشن خودش می‌سازد، نه چیزِ دیگری:

کدapp/Models/Product.php
use Illuminate\Database\Eloquent\Relations\BelongsToMany;

public function tags(): BelongsToMany
{
    return $this->belongsToMany(Tag::class);
}
کدapp/Models/Tag.php
public function products(): BelongsToMany
{
    return $this->belongsToMany(Product::class);
}
  • اسمِ جدولِ واسط از ترکیبِ حروف‌الفباییِ دو نام می‌آید: product_tag (اگر خواستی اسمِ دیگری بده: belongsToMany(Tag::class, 'table_name')).
  • ستون‌ها: نامِ مفردِ مدل + _id یعنی product_id و tag_id.
  • هر تگِ خوانده‌شده یک ویژگیِ pivot هم دارد (دسترسی به واسط).
بساز و نام بگذار

جدولِ واسط مایگریشن می‌خواهد: php artisan make:migration create_product_tag_table، بعد foreignId برای هر دو و unique روی جفت — تا یک «اتصال» دوبار ثبت نشود. در گامِ پروژه لازمش نیست؛ اگر دوست داشتی خودت کاملش کن.

۵

attach / detach / sync

برایِ «ربطِ» رکوردها در رابطه‌ی چند‌به‌چند این متدهاست:

کدPHP
$product = Product::find(1);
$tag     = Tag::find(2);

$product->tags()->attach($tag);            // یک ردیف در product_tag
$product->tags()->attach([3, 4]);          // یا با آرایه‌ای از id
$product->tags()->attach([5 => ['note' => 'ویژه']]); // با ستونِ اضافه

$product->tags()->detach(2);               // برداشتنِ پیوندِ مشخص
$product->tags()->detach([3, 4]);

$product->tags()->sync([4, 5, 6]);         // فقط همین‌ها بمانند؛ بقیه جدا/اضافه شوند
  • attach/detach بدونِ لمسِ خودِ رکوردها فقط پیوند را می‌سازد/می‌کند.
  • sync([...]) وضعیتِ نهایی را تحمیل می‌کند — برایِ صفحه‌ی «برچسب‌هایِ این محصول» که از فرم می‌آید کامل است.
  • کلیدِ واسط، یک pivot مدل است؛ ستونِ اضافه را با ->withPivot('note') معرفی کن.
۶

مشکل N+1 و Eager Loading با with()

فرض کن صفحه‌ی «فهرستِ دسته‌بندی‌ها» هست که برایِ هر کدام، اولینِ محصولش را نشان می‌دهد:

کدبلید — روشِ ساده (و پرکوئری!)
@foreach ($categories as $category)
    <p>{{ $category->name }}
       — {{ $category->products()->first()?->name }}</p>
@endforeach
# ۱۰ دسته‌بندی داریم → ۱۱ کوئری: 1 select * from categories 2 select * from products where category_id = 1 limit 1 …و باز برای ۲، ۳، ۴، ... تا ۱۰

به این می‌گویند مشکلِ N+1: یک کوئری برایِ فهرست + یک کوئری به ازایِ هر ردیف. راهِ درست: Eager Loading — رابطه‌ها را قبل، به‌صورتِ دسته‌ای، در ۲ کوئریِ کل بکش:

کدکنترلر
$categories = Category::with('products')->get();
// 1 کوئری برای دسته‌بندی‌ها + 1 کوئری برای همه‌ی محصول‌هایِ متعلق به آن‌ها

حالا در بلید، به‌جایِ products() از products (بدون پرانتز) استفاده کن که همان Collectionِ بارگذاری‌شده را بردارد — بدونِ کوئریِ اضافه:

کدبلید
@foreach ($categories as $category)
    <p>{{ $category->name }} — {{ $category->products->first()->name ?? 'بدون محصول' }}</p>
@endforeach
تشخیصِ بموقع

در توسعه، لاراول می‌تواند lazy loading (همان کوئریِ خودسرِ در حلقه) را با Model::preventLazyLoading() خطا کند — یعنی بلافاصله می‌فهمی کجا و به‌چه رابطه‌ای «دیر» رسیدی. این را در AppServiceProvider::boot() برایِ local روشن کن.

۷

Accessor و Mutator: دگرگونیِ مقدار

گاهی موقعِ خواندن یا نوشتن یک ستون، چیزی بیشتر از مقدارِ خام می‌خواهیم. در لاراول ۱۳ این با کلاسِ Attribute انجام می‌شود (همان الگویِ Attribute::make):

کدapp/Models/Product.php
use Illuminate\Database\Eloquent\Casts\Attribute;

// Accessor: هر وقت خواستی «برچسبِ قیمت»، این را تحویل بگیر
protected function priceLabel(): Attribute
{
    return Attribute::make(
        get: fn () => number_format($this->price) . ' تومان',
    );
}

// Accessor برایِ عکس: مسیرِ کامل را برگردان (نه نامِ فایلِ خام)
protected function image(): Attribute
{
    return Attribute::make(
        get: fn (?string $value) => $value
            ? '/storage/' . $value
            : '/images/placeholder.png',
    );
}

// Mutator برایِ قیمت: مقدارِ دریافتی را تمیز کن، بعد ذخیره کن
protected function price(): Attribute
{
    return Attribute::make(
        set: fn ($value) => max(0, (int) $value),
    );
}
  • Accessor = کلیدِ get: مقدارِ ستونِ خام را می‌گیرد و به‌هایِ جدید برمی‌گرداند؛ وقتی می‌گویی $product->price_label (بخوان) اجرا می‌شود.
  • Mutator = کلیدِ set: موقعِ نوشتن اجرا می‌شود؛ خروجیِ یکتا یا آرایه‌ای از جفت‌های ستون/مقدار برایِ ذخیره باشد.
  • نامِ متد = نامِ attribute با camelCase: ستونِ price_label ← متدِ priceLabel.

در بلید چه می‌کنیم؟ هیچ چیزِ خاصی؛ همین‌طور:

کدBlade
<p>{{ $product->price_label }}</p>
<img src="{{ $product->image }}" alt="">
یک‌جا فکر کن، نه در بلید

هر الگویِ نمایشیِ تکراری («۳۵۰٬۰۰۰ تومان»، «مسیرِ عکس» و...) را به‌جایِ کپی‌کردن در هر بلید، همین‌جا تعریف کن — ساختار مرتب می‌ماند و هر تغییری فقط در یک‌جا لازم می‌شود.

۸

آزمایشگاه با php artisan tinker

حالا همه‌چیز را در Tinker «متحرک» ببین — نه فقط بخوان، رابطه‌ها و کوئری‌ها را هم بساز:

$ php artisan tinker >>> $c = App\Models\Category::find(1); => App\Models\Category {#1 id: 1, name: "کالای دیجیتال" } >>> $c->products->count(); => 5 >>> $c->products()->orderByDesc('price')->first()->price_label; => "1,250,000 تومان" >>> App\Models\Product::first()->category->name; => "کالای دیجیتال" >>> $product = App\Models\Product::first(); >>> $product->tags()->attach([1, 2]); // پیوند ساخته شد (چیزی چاپ نمی‌شود) >>> $product->tags->pluck('name')->all(); => ["ویژه", "پرفروش"]
چرا «آزمایشگاه»؟

هر کوئریِ چندخطی و رابطه‌ای، اول در Tinker. خطایِ کوئری در یک بلیدِ پیچیده سخت‌تر دیده می‌شود؛ اینجا در دو دقیقه به جوابِ درست می‌رسی و بعد کدش را به کنترلر منتقل می‌کنی.

۹

گام پروژه: روابطِ فروشگاه

دسته‌بندی و محصول، حالا با هم

این همان نقطه‌ای است که «فروشگاه کوچک» زنده می‌شود: رابطه‌ها را وصل کن، قیمت همیشه مرتب باشد، عکس خودش مسیرِ درست را بداند.

  1. در Category: products() با hasMany(Product::class)؛ در Product: category() با belongsTo(Category::class).
  2. priceLabel() (accessor) و image() (آدرسِ کاملِ تصویر یا placeholder) را به Product اضافه کن؛ در product-card.blade.php درس ۰۶ از $product->price_label استفاده کن.
  3. صفحه‌ی «دسته‌بندی‌ها»: Category::with('products')->get() به‌همراهِ {{ $category->products->count() }} — بدون N+1.
  4. صفحه‌ی محصول: Product $product (Bindingِ درس ۰۸) و نمایشِ {{ $product->category->name }}.
  5. اگر حسِ ماجراجویی داری: جدولِ واسطِ product_tag با make:migration create_product_tag_table بساز، مدلِ Tag و belongsToMany را وصل کن، و در Tinker attach/sync را بچش.
بعدی

فرم‌ها و اعتبارسنجی در درس ۱۰، وب را «تعاملیِ واقعی» می‌کند: ایجادِ محصول از درونِ خودِ سایت تا لینک‌های store/update/destroy غریزه‌ات شوند. عکسِ واقعی هم در درس ۱۴ (آپلود) می‌رسد.

۱۰

تمرین‌ها؛ حالا نوبت توست!

تمرین ۱: دیدگاه‌ها زیرِ محصول
  1. در Product متدِ reviews(): HasMany (مدلِ Review از درس ۰۷) را بساز.
  2. در Review متدِ product(): BelongsTo را بساز.
  3. در Tinker: Product::find(1)->reviews و Review::first()->product->name را بزن.
تمرین ۲: N+1 را شکار کن
  1. بلیدی بساز که برایِ هر دسته‌بندی، تعدادِ محصول‌هایش را چاپ کند؛ اول بدون with.
  2. Model::preventLazyLoading() را در بوتِ AppServiceProvider (محیطِ local) روشن کن — خطا می‌گیرد؟
  3. با ->with('products') همان خروجی را بدونِ خطا بگیر و مطمئن شو فقط ۲ کوئری زده شد.
چالش

ستونِ slug را در Category بساز و یک accessor به نامِ url() بنویس که آدرسِ «/categories/{slug}» را برگرداند؛ یعنی لینک در بلید به‌جای هاردکد نوشته می‌شود.

چیزی که از این بخش توی ذهنت بماند

  1. رابطه = متدِ Eloquent رویِ مدل؛ hasMany (بسازد) در والد، belongsTo (متعلق) در فرزند.
  2. hasOne برایِ یک‌به‌یک؛ belongsToMany برایِ چند‌به‌چند با جدولِ واسط (به‌همراهِ pivot).
  3. ربط‌ها: attach (پیوند)، detach (گسستن)، sync (تحمیلِ وضعیتِ نهایی).
  4. مشکلِ N+1 = کوئریِ به‌ازای‌هرشیء؛ راهش ->with('relation') و خواندنِ property (بدونِ پرانتز).
  5. Accessor (get) موقعِ خواندن، Mutator (set) موقعِ نوشتن — با کلاسِ Attribute.
  6. Tinker همان «دستِ آزمایشگاه» است: قبل از کنترلر، کوئری و رابطه را آن‌جا امتحان کن.
